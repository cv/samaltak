# NVIDIA's CUDA libraries from Smalltalk

Samaltak calls NVIDIA's CUDA libraries — the runtime, the driver API, cuBLAS, cuRAND, cuSOLVER, cuFFT and cuOpt
so far; cuSPARSE next — through approved FFI exports generated from NVIDIA's own headers. They use NVIDIA's CUDA
userspace (libcudart, libcuda), not System-NV's RM ioctls (docs/nv.md); where they are, NvComputeGPU's kernels (the
World's rendering) run on them too (NvCompute and libcuda, below), else on the RM ioctls. This
was a spike on the DGX Spark (GB10, CUDA 13.0, driver 580.178.04); the result is solid enough to keep.

```smalltalk
Cuda summary.
"'NVIDIA GB10, compute 12.1, 48 SMs, 130.7 GB (15.6 GB free); CUDA runtime 13.0, driver 13.0; cuBLAS 130101; cuRAND 10400'"

| a b |
a := CudaMatrix rows: 2 cols: 3 values: #(1 2 3 4 5 6).
b := CudaMatrix rows: 3 cols: 2 values: #(1 0 0 1 1 1).
(a * b) asRows.                                   "#(#(4.0 5.0) #(10.0 11.0))"
a * b.                                            "a CudaMatrix float32[2x2] (16 bytes) ((4.0000 5.0000) (10.0000 11.0000))"

(CudaMatrix uniformRows: 4096 cols: 4096) * (CudaMatrix uniformRows: 4096 cols: 4096).
CudaBenchmark report.                             "the numbers below"

((CudaMatrix fromRows: #(#(2 1) #(1 3)) type: #float64) solve: (CudaArray withAll: #(3 5) type: #float64)) asArray.
"#(0.8 1.4)"                                      "LU on cuSOLVER; also inverse, determinant, qr, svd, cholesky, symmetricEigen"
(CudaArray withAll: #(1 2 3 4)) fft.              "a CudaArray complex64[3] (24 bytes) (10.0000+0.0000i -2.0000+2.0000i -2.0000+0.0000i)"

CuOpt maximize: #(3 5) subjectTo: #(#(1 0) #(0 2) #(3 2)) atMost: #(4 12 18).
"a CuOptResult: OPTIMAL, objective 36.0 at #(2.0 6.0) in 534 ms"
```

## How the binding works

Four layers, three of them generated by `tools/cuda/bindgen.py` from `tools/cuda/bindings.spec`:

1. **The spec** lists, per library, its header, sonames, status type, handle types and the functions to bind, with
   an annotation where the C type does not say what a parameter is: `alpha=value` (a `const float *` passed by
   value), `A=dev:MAT(lda,m,k)` (a device pointer and the extent the call touches), `dst=outarray:count` (a host
   buffer), `problem_ptr=handleout:num_variables` (a new handle remembering a number), `require=...` (a condition on
   the arguments), `as cudaMemcpyHtoD ... kind=const:cudaMemcpyHostToDevice` (a variant with a fixed argument),
   `inembed=null`; expressions may name the header's constants (`side==CUBLAS_SIDE_LEFT`), a handle's tag
   (`TAG(plan)`) and cudalib.h's helpers (`cudalib_dtype_bytes(MAT(lda,m,n),dataTypeA)`: bytes of a cudaDataType).
   Unannotated parameters follow from their types: integers, enums, `float`/`double` by value, handles,
   `T *` as an out-parameter (runtime, driver API, cuOpt) or a device pointer (cuBLAS, cuRAND), `const char *` as a
   String. It is a list of functions per library: adding one is a line.
2. **The generator** preprocesses each header with the C compiler (`cc -E`; `-dM` for macros such as
   `#define cublasSgemm cublasSgemm_v2`, so the real symbol is bound), parses the prototypes, typedefs and enums, and
   writes
   - `vm/native/cudalib_gen.c`/`.h`: one C wrapper per function, typed per the header. It loads the library with
     dlopen on first use (`cudalib.c`: `SAMALTAK_CUDA_LIBS`'s directories, then the loader's path, then
     `/usr/local/cuda/lib64`), finds the symbol, **checks every argument** and calls it. No CUDA header is
     needed to build the VM, and on UEFI the wrappers are stubs.
   - `src/VM-Jit/CudaBackend.st` and `FFIPrimitives-cuda.extension.st`: the wrappers as `vm:core` approved
     exports `cuda_<function>` (keys 800–1030: cuSOLVER from 960, cuFFT from 1010; append only), each with its
     exact tag signature.
   - `src/System-CUDA/CudaRuntimeAPI.st`, `CudaDriverAPI`, `CublasAPI`, `CurandAPI`, `CusolverAPI`, `CufftAPI`,
     `CuOptAPI`: one class-side
     method per function (`CublasAPI cublasSgemm: handle transa: 0 transb: 0 m: n: k: alpha: a: lda: ...`) with
     a literal `ffiSite:`, so the optimizing JIT calls the wrapper directly.
   `tools/cuda/bindgen.py --check` says whether the committed files are current; regenerate where the headers are
   (the toolkit; cuOpt's wheel for cuOpt, `CUOPT_PREFIX`), then `make translate`.
3. **The checks** (`vm/native/cudalib.h`) keep the FFI's rule that the image never holds a raw native pointer
   that can hurt the VM:
   - handles (`cublasHandle_t`, `cudaEvent_t`, `cuOptSolution`, ...) live in a table in the VM; the image holds
     an id (serial << 12 | slot), so a forged, stale or wrong-type id is refused; cuFFT's plans are `int`s, kept
     there the same way (as 1 << 32 | plan), with a tag: the plan's type and array sizes;
   - device pointers are Integers, but every one must lie inside a live allocation that `cudaMalloc` made, and the
     extent the call will touch (`MAT(ld, rows, cols)` for a matrix, `count` for a copy) must fit in it: a
     wrong shape is refused before cuBLAS sees it, it never writes past an allocation (on the GB10 the GPU shares the
     process's memory, so an unchecked pointer would be a stray write anywhere); extents are computed without
     overflow (a forged leading dimension of 2^62 is refused, not wrapped);
   - host buffers are FFI slices of ByteArrays and must be long enough for the count; strings are copied and
     NUL-terminated; cuOpt's CSR matrix is checked (offsets from 0, never decreasing, column indices in range).
   A refused call answers -3 to -7 and never reaches the library. Not checked: what a library does with valid
   arguments (a kernel that faults poisons the CUDA context, as in C), and calls block the VM thread (cudaMemcpy,
   cuOptSolve; `CudaEvent wait` polls instead).
4. **The Smalltalk API** (`System-CUDA`, hand-written): `CudaError` (the library's own name and description of
   the status: `cudaMalloc: cudaErrorMemoryAllocation (out of memory)`, `cublasGetStatusName/String`, the enum's
   names for cuRAND, cuOpt's status macros) with `CudaUnavailable` and `CudaArgumentError`; `Cuda` (the device,
   the session's cuBLAS handle, cuRAND generator and cuSOLVER handle); `CudaArray`/`CudaMatrix`; `CudaEvent`; `CuOpt`;
   `CudaLU`, `CudaDecomposition`, `CudaFFTPlan` and `CudaSolverError` (below); `CudaBenchmark`.

**Context.** The runtime's implicit primary context on device 0; no CudaContext class. cuBLAS, cuRAND, cuOpt and the
image's own kernels (NvCudaCompute) all run in it, on the default stream (`cudaStreamCreate`, `cublasSetStream` and `curandSetStream` are bound for
streams).

**Device memory as objects.** `CudaArray new: n type: #float32` (or `#float64`, `#complex64`, `#complex128`;
`#int32` and `#int64` for pivots and devInfo) is device memory with a count and type; `withAll:` copies Smalltalk numbers to the device, `asArray`/`first:`/`at:` copy back, `fillUniform`
fills on the device (cuRAND), `norm`, `+`, `-` run there (cuBLAS). `printString` (and so the Inspector) shows the
type, shape, size and the first values (a matrix's top-left corner). `release` frees at once; an unreleased array
is freed when collected (`WeakRegistry`, `CudaReleaser`). Each object remembers the VM session
(`cuda_session`): after a snapshot is restored, it is dead (`isAlive` false, "released"), never a dangling address.

**Row-major.** `CudaMatrix` is row-major, as Smalltalk writes a matrix (element i, j at (i - 1) * cols + j) and as
`fromRows:`/`asRows` read. cuBLAS is column-major, where a row-major m x k matrix in memory is its k x m
transpose. So `C := A * B` is computed as the column-major `C^T = B^T A^T`: `cublasSgemm(N, N, n, m, k, 1, B, n,
A, k, 0, C, n)` — the same gemm with the operands swapped, no transposes and no copies. Users of `CublasAPI`
directly get cuBLAS's column-major convention, as in C.

## Numbers (DGX Spark, GB10)

`CudaBenchmark report` in the image (`--jit opt`) against `tools/cuda/sgemm_sample.c` (the same in C), with a quiet
machine and GPU:

| | Smalltalk (bindings) | C (CUDA's own) |
| --- | --- | --- |
| SGEMM 4096 x 4096, device time (CUDA events), 20 products | 7.52 ms, **18.3 TFLOPS** | 7.39 ms, 18.6 TFLOPS |
| SGEMM 1024 x 1024, 50 products | 0.138 ms, 15.6 TFLOPS | 0.128 ms, 16.8 TFLOPS |
| queuing one SGEMM (8 x 8: launch cost) | 4.6 µs | 3.3 µs |
| a trivial call (cudaGetDevice) | 0.077 µs | 0.025 µs |
| CPU: naive Smalltalk loop, 128 x 128 | 5.8 ms, 0.73 GFLOPS (4096: ~3 minutes) | |
| CPU: Ubuntu's reference BLAS (`libblas.so.3`, one core), 1024 | | 0.36 s, 6.0 GFLOPS |

The binding costs about 50 ns a call (the FFI's checked wrapper plus the VM's handle and extent checks) and about
1.3 µs a matrix product (CudaMatrix's shape checks, the session's handle, three checked device pointers): nothing
next to a large product, and the 4096 product runs at C's speed. The GPU is about 25,000 times the naive Smalltalk
loop and 3,000 times the reference BLAS (no optimized CPU BLAS is installed). Correctness: a random 96 x 96 product
matches the Smalltalk loop within 6.3e-6 in float32 and 1.1e-14 in float64 (`CudaBenchmark check:type:`,
`CudaGpuTest`). Under load (a gate running) the 4096 product took 9.2 ms in both. The first CUDA call in a
process costs 0.23–0.28 s (context creation), in C as well.

Note: `cudaMemGetInfo`'s "free" on the GB10 is the system's free memory (unified memory: 0.7–15 GB of 130.7
while the page cache holds the rest), not what an allocation can get.

## cuSOLVER and cuFFT

Dense factorizations (cuSOLVER's `cusolverDn`) and Fourier transforms (cuFFT) on CudaMatrix and CudaArray, float32
and float64:

```smalltalk
| a lu d |
a := CudaMatrix fromRows: #(#(4 3) #(6 3)) type: #float64.
lu := a lu.                     "a CudaLU of a float64[2x2] matrix: P A = L U, kept on the device"
lu determinant.                 "-6.0"
(lu solve: (CudaArray withAll: #(10 12) type: #float64)) asArray.    "#(1.0 2.0)"
lu inverse asRows.              "#(#(-0.5 0.5) #(1.0 -0.6666666666666666))"
lu l asRows. lu u asRows. lu permutation.
lu release.
a solve: aMatrixOfRightHandSides. a inverse. a determinant.         "lu, then getrs"
(CudaMatrix uniformRows: 2048 cols: 1024) svd.  "a CudaDecomposition svd: u float32[2048x1024]; s float32[1024]; vt float32[1024x1024]"
m qr. m cholesky. m symmetricEigen. m singularValues.

(CudaMatrix uniformRows: 4096 cols: 4096) fft.  "the 2-D half spectrum: a CudaMatrix complex64[4096x2049]"
f ifftReal: 4096. c fft. c ifft. m fftRows.     "back; complex; inverse (normalized); each row, batched"
```

- **Bindings.** cuSOLVER's 64-bit API for LU (`cusolverDnXgetrf`/`Xgetrs`), Cholesky (`Xpotrf`/`Xpotrs`) and QR
  (`Xgeqrf`), where a `cudaDataType` argument chooses float32 or float64 and the workspace's size is an argument in
  bytes, so the VM checks it (`bufferOnDevice=dev:workspaceInBytesOnDevice`; the host workspace is a ByteArray). The
  legacy API for what the 64-bit one lacks or takes too many arguments for (the FFI's 16 slots): `S/Dorgqr` (Q),
  `S/Dgesvd` (16 arguments exactly), `S/Dsyevd`; each takes its `lwork`, so its workspace is checked too.
  `devInfo` is a 1-element `#int32` CudaArray the image reads back. cuFFT: `cufftPlan1d/2d/Many` (rank 1 to 3,
  batched), `cufftExec{R2C,C2R,C2C,D2Z,Z2D,Z2Z}`, `cufftDestroy`, `cufftSetStream`. A plan's handle carries a tag
  (`cudalib_fft_tag`: type << 56 | half << 28 | n): an exec is refused on a plan of the other kind
  (`CUDALIB_FFT_TYPE(TAG(plan))==CUFFT_R2C`) or on arrays shorter than the plan's (n reals or complex values,
  half: the last dimension // 2 + 1 complex values), so cuFFT never writes past an allocation; arrays are limited to
  2^28 elements. cuBLAS gained `geam` (transposes), `copy` (strided: diagonals, real and imaginary parts),
  `trmm` and `scal` (also `Csscal`/`Zdscal`).
- **Row-major.** cuSOLVER is column-major. A row-major matrix's memory is its transpose column-major, so a
  factorization runs on `transposed` (cuBLAS geam into a new matrix, which getrf may overwrite anyway): P A = L U
  of the matrix as Smalltalk reads it. Results come back the other way: a column-major result read row-major is its
  transpose, which is sometimes what is wanted (the wide SVD's U and Vt need no transpose at all) and otherwise one
  geam. Triangles (L and U of an LU, R of a QR, Cholesky's L) are `trmm` of the triangle, transposed, by the
  identity: the column-major product `tri(A)^T` is `tri(A)` row-major, zeros and all. A symmetric matrix is its own
  transpose: `cholesky` and `symmetricEigen` read it as is.
- **Complex numbers.** `#complex64` / `#complex128` CudaArrays hold interleaved (real, imaginary) float or double
  pairs, as cuFFT and cuBLAS do; their values are Smalltalk `Complex` numbers (`asArray`, `withAll:` takes Complex
  or real numbers), their printString (and so the Inspector) shows `1.5000-2.0000i`; `asComplex`, `real`,
  `imaginary` and `norm` work on the device. `fft` of a real array is the half spectrum (n // 2 + 1 values, like
  numpy's rfft), of a complex one the full transform; `ifft` and `ifftReal:` are normalized (1/n), so
  `a fft ifftReal: a size` is `a`. `fft` and `ifft` use the session's plans, kept by shape, kind (r2c, c2r, c2c:
  both directions), type and batch (`Cuda fftPlan:kind:type:batch:`, the last `Cuda fftPlanLimit` = 8, least
  recently used out first: each holds its work area on the device; `Cuda releaseCaches` frees them, a new session has
  none): planning a 4096 x 4096 transform costs 7 ms, more than the transform. A `CudaFFTPlan` of one's own is
  released by its maker.
- **Work areas.** cuSOLVER's calls (`lu`, `cholesky`, `qr`, `svd`, `symmetricEigen`) take their device work area
  from the session's one (`Cuda workspace:`, grown as asked, up to `Cuda workspaceLimit`, 1 GB) and ask each
  `*BufferSize` once a routine, shape and type (`Cuda bufferSize:ifAbsent:`): calls on the one stream run one after
  another, so each can use it whole; no cudaMalloc/cudaFree (which waits for the device) a call.
- **Errors.** A routine that ran but reports failure in devInfo signals a `CudaSolverError` saying what cuSOLVER's
  documentation says devInfo means there: `CudaSingularMatrix` (`cusolverDnXgetrf: the matrix is singular: U(2,2)
  is exactly zero (devInfo 2)`), `CudaNotPositiveDefinite` (potrf: the leading minor of order i is not), no
  convergence (gesvd, syevd), a wrong parameter (negative). A singular matrix has an LU (`isSingular`,
  `determinant` 0.0); solving with it or inverting it signals.
- **Tests.** `CudaSolverGpuTest` and `CudaFFTGpuTest` (test-nv) check every factorization in both precisions against
  Smalltalk references (products, Gaussian elimination, Jacobi eigenvalues, a summed DFT), the error paths and the
  plan checks; `CudaBindingTest` the refusal of forged cuSOLVER handles and cuFFT plans without a GPU.

Numbers: `CudaBenchmark solverReport` against `tools/cuda/solver_fft_sample.c` (the same in C, with LAPACK and FFTW
on the CPU), float32 unless said:

| | Smalltalk (bindings) | C (CUDA's own) | CPU |
| --- | --- | --- | --- |
| LU 4096 x 4096 (`lu`: transposed copy and getrf) | 16.9 ms | getrf 13.7 ms, 3.3 TFLOPS | Smalltalk loop ~1.8 min (2048: 13.9 s); LAPACK (reference) 6.1 s |
| solve one right-hand side with it (getrs) | 2.2 ms | 0.79 ms | LAPACK 5.7 ms |
| LU 4096, float64 | 134 ms | | |
| SVD 2048 x 1024, thin U, S, Vt (gesvd) | 131 ms | 119 ms | Smalltalk one-sided Jacobi ~1.3 min (512 x 256: 1.3 s); LAPACK (reference) 5.7 s |
| singular values only | 69 ms | 66 ms | |
| SVD 2048 x 1024, float64 | 509 ms (values only 124 ms) | | |
| 2-D FFT 4096 x 4096, real to complex, plan kept | 1.83 ms, 549 GFLOPS (2.5 N log2 N) | 1.81–1.88 ms | Smalltalk radix 2 (complex, float64) 5.5 s; FFTW 69 ms, 15 ms on 20 threads |
| `CudaMatrix fft`, its plan kept (the session's) | 5.0 ms (a new 64 MB result each call: 3 ms of it) | | |
| `CudaMatrix fft`, planning first (as every call did before) | 7.9 ms (8.3 before, on a quieter GPU) | plan 6.8 ms | |

The transforms and the SVD run at C's speed. `lu` costs 3 ms more than the bare getrf: the 64 MB transposed copy it
factors (an allocation and a geam); `solve:` 1.4 ms more than getrs (the right-hand side's copy, devInfo read back).
The GPU is 400 times reference LAPACK at LU, 44 times at SVD, and 38 times FFTW on one core at the FFT (8 times on
20), and about 6,000 / 600 / 3,000 times the Smalltalk loops. Accuracy: the 4096 solve's relative residual
|A x - b| / |b| is 6.6e-7 in float32 and 1.2e-15 in float64; the SVD's sum of s^2 is |A|^2 (Frobenius) within
1.2e-7 / 5e-16, its singular values those of the Smalltalk Jacobi within 1e-14 (float64); the FFT's round trip is
within 3e-7 and a 256 x 256 transform the Smalltalk FFT's within 5e-8. Times vary with the shared GPU's load and
clocks (the C SVD took 119 to 250 ms over runs).

## Element-wise expressions: one kernel each

`CudaArray` (and `CudaMatrix`) arithmetic is element-wise and lazy: `+ - * /` with numbers and arrays (`2 * a` and
`1 - a` too), `min:` `max:` `raisedTo:`, `negated abs sqrt squared reciprocal exp ln log sin cos tanh`, the
comparisons `< <= > >= eq: ne:` (masks: 1.0 where true, else 0.0; `=` stays identity's) and `mask where: x else: y`
answer a *pending* array: a `CudaExpression` tree over its operands, a pending operand's tree taken in. Its values
are computed when they are needed (its address: `printString`, `asArray`, a cuBLAS or cuFFT operand, a kernel
argument) or when asked (`realize`, `value`; `storeInto: anArray` writes them into an array one has, in place too),
by one kernel for the whole expression, launched once. `sum`, `max`, `min` and `mean` of a pending array reduce in
the same kernel (each block's partial result in float64, the last step on the host): the values are never stored.
On a `CudaMatrix`, `*` of a matrix is still the matrix product (`mul:` is the element-wise one), `*` of a number
element-wise.

```smalltalk
| a b c |
a := CudaArray uniform: 1000000 type: #float32. b := CudaArray uniform: 1000000 type: #float32.
c := ((a * 2 + b) sqrt - 1) max: 0.25.     "pending: nothing ran"
c first: 4.                                "one kernel computed c"
((a - b) abs > 0.5) mean                   "one kernel, about 0.25"
(m + aRow) * 2                             "a row (an array of m's columns' count) broadcast down m"
```

- **The kernel** (`CudaExpression>>cudaSource:`) is CUDA C++ written from the tree: a grid-stride loop over the
  output, each array operand loaded once at its index (`i`, a row's `i % cols`, a column's `i / cols`, one value's
  `0`), the operations in the output's type (float32 with float64 is float64, a number takes the array's type),
  stored, or folded into the reduction. Shapes broadcast as numpy's: equal shapes, a number or a one-value array, a
  row (n or 1 x n) or a column (n x 1) against a matrix; others are an error when the expression is made.
- **Compiled once a shape.** The kernel's key, its *signature*, is the output's type, the reduction, each array's
  type and index and the C++ of the tree: not the sizes or the numbers, which are arguments (`a * 2 + b` and `a * 3
  + b` of any length share one). `Cuda fusedKernel:source:` keeps the session's kernels by signature (the last
  256), their cubins by the source's SHA-256 in `Cuda compiler`, an `NvRtcCache` (System-NV): the NV shaders'
  machinery, which `NvShaderCompiler` now uses too (a compile under way is waited for, not run twice, failures are
  kept, `isReady:` compiles in the background).
- **Correctness.** A pending array reads its operands when it is computed, so it is computed first when an operand
  is about to change or go: `release`, and anything but a fused kernel asking for the operand's address
  (`fromArray:`, `fillUniform`, a cuBLAS product into it, a kernel argument) computes the arrays pending on it
  (`realizeReaders`; reads such as `asArray`, `norm` or a product's operands use `readAddress` and leave them
  pending). Trees past 64 operations or 16 arrays compute their pending operands first.
- **Falling back.** Where no kernel can be made (no NVRTC; a compile error: `CudaExpression lastFailure`) each
  operation runs by itself, its own kernel, else cuBLAS (`+`/`-` of two arrays: a copy and axpy; `*`/`/` by a
  number, `negated`: a copy and scal; anything else is an error). Complex arrays still add and subtract with cuBLAS
  at once; other element-wise operations on them, and integer arrays, are refused. `CudaExpression fusing: false`
  computes every operation at once, a kernel each (to compare, or to find a fault); `CudaExpression launches` counts
  the kernels and cuBLAS calls run for expressions.
- **Tests.** `CudaExpressionTest` (test-core, no GPU: broadcasting, types, signatures, the C++ written);
  `CudaFusionGpuTest` (test-nv: values against Smalltalk's, one launch an expression and a kernel a shape, masks,
  broadcasting, reductions, computing before an operand changes or goes, the fallbacks, the kept FFT plans and work
  area).

Numbers (`CudaBenchmark fusionReport`, the best of three runs on the shared GPU): `((a * 2 + b) sqrt - 1) max: 0.25`,
five operations, on two float32 arrays:

| | 1 M floats | 64 M floats |
| --- | --- | --- |
| fused, into a new array (1 launch) | 0.83 ms | 19.1 ms |
| fused, `storeInto:` an array kept | 0.56 ms | 3.68 ms (805 MB moved: 219 GB/s, a device copy's speed) |
| an operation at a time (`fusing: false`: 5 launches, 5 new arrays) | 2.09 ms | 61.6 ms |
| the shape's first call (NVRTC compiling) | 29.3 ms | 29.5 ms |
| its `sum`, fused (1 launch, nothing stored) | 0.43 ms | 2.93 ms |
| its `sum` after computing its values | 1.44 ms | 19.0 ms |

Fused is 3.2 times one kernel an operation into new memory, 17 times into an array kept; the reduction 6.5 times.
A new 256 MB array costs about 15 ms (cudaMalloc and cudaFree on the GB10's unified memory: 190 ms when the
machine is loaded), more than the kernel: `storeInto:` an array one keeps is the way for big arrays in a loop. A
kernel's compile (about 29 ms) is paid once a shape a session, and not again for a source already compiled in the
image (`Cuda compiler`). Before, only `+` and `-` existed (cuBLAS: a copy and an axpy, two calls an operation).

## cuOpt

NVIDIA's open-source cuOpt (Apache-2.0) has aarch64 builds for CUDA 13: the wheel `libcuopt-cu13` (26.10.1) from
pypi.nvidia.com, with a C API (`cuopt/mathematical_optimization/cuopt_c.h`, `libcuopt_mathopt.so`: LP, MILP and QP;
routing is C++/Python only). Installed privately, no sudo, no system change:

```sh
P=~/.local/share/samaltak-cuopt; mkdir -p $P && cd $P
uv venv --python 3.12 venv && VIRTUAL_ENV=$P/venv uv pip install --extra-index-url https://pypi.nvidia.com libcuopt-cu13
export SAMALTAK_CUDA_LIBS=$P/venv/lib/python3.12/site-packages/libcuopt_mathopt/lib64
```

That is 2.4 GB: the library (277 MB) and its dependencies as wheels (RMM, RAFT, cuDSS 65 MB, NCCL 189 MB) and a second
CUDA 13 set (runtime 13.5, cuBLAS 13.10, cuSPARSE, cuSOLVER, cuRAND; 1.7 GB). Its RPATH finds them; where the
toolkit's libcudart.so.13 is loaded first (by `Cuda`), cuOpt uses that one, and it works with driver 580 either way
(CUDA's minor-version compatibility). `CuOpt` builds the CSR matrix from dense rows and solves; `CuOptGpuTest`
covers a maximization, a minimization, an infeasible problem and a refused matrix. A small LP takes 0.1 s, the first one
in a process 0.5 s (cuOpt's initialization; it runs PDLP, dual simplex and barrier concurrently). Found on the way: an upper bound of 1e30 instead of
infinity made cuOpt's presolve drop a constraint (objective 42 instead of 36); `CuOpt` uses `Float infinity`.

## The next libraries

Each is a `lib` block and a few `fn` lines in the spec; what they need beyond that:

- **cuSOLVER, more**: the sparse (`cusolverSp`) and multi-GPU APIs; `gesvdj` (Jacobi: faster for small and
  batched SVDs), batched `getrf`/`potrf` (`cusolverDnXpotrfBatched`'s arrays of pointers need a checked
  pointer-array role); complex factorizations (the legacy `C`/`Z` functions; the 64-bit API takes complex types
  already).
- **cuFFT, more**: 3-D transforms are bound (`cufftPlanMany`, rank up to 3) but not wrapped; advanced layouts
  (`inembed`, strides) would need the tag to describe them; callbacks are device code (NvCompute's NVRTC).
- **cuRAND**: bound (uniform and normal, float and double); quasi-random generators need
  `curandSetQuasiRandomGeneratorDimensions`, one line. Normal generation wants an even count.
- **cuSPARSE** (generic API): descriptors (`cusparseCreateCsr`, `cusparseCreateDnVec`) are handles made from device
  pointers; the descriptor should remember its arrays' extents (a handle's tag, as cuOpt's problems remember their
  variable count) so `cusparseSpMV` can be checked.
- **Asynchrony**: long calls (cuOptSolve, a cuSOLVER factorization with a sync) block the VM thread. The NVRTC pattern
  (`vm/native/nvrtc.c`: a thread a job, the image polls) generalizes: a spec flag `async` that runs the call on a
  worker and answers a job to poll.
- Not installed here: cuDNN, NCCL (only as cuOpt's dependency), TensorRT. cuDNN's graph API (`cudnnBackend*`)
  is attribute-setting through `void *` arrays: it needs a typed Smalltalk layer of its own.

## The GPU demos in the World

World menu › Apps › **GPU** (shown where `Cuda isAvailable`; `GpuTools`, package Tools-CUDA, layer 5; `Tools open:
#gpuWorkspace`, `#cuopt`, `#gpuMonitor`, `#spectrum`):

- **GPU Workspace** (`GpuWorkspace`): a Workspace of ready-to-run snippets, a section for each library this VM has
  (cuBLAS, cuRAND, cuSOLVER, cuFFT, cuOpt). `CudaComparison` times an operation on the GPU (CUDA events,
  the median of 3–7 runs after a warm-up) and as a Smalltalk loop on the CPU (past a size, measured smaller and
  extrapolated, as it says), with the speedup and a check of the result:
  `SGEMM 1024x1024: GPU 0.142 ms (15.1 TFLOPS) · CPU 3.54 s (Smalltalk loop at 256, x64; 606.9 MFLOPS) · 24,948x
  faster · corner within 2.7e-6 relative`; 4096: 7.0 ms (19.6 TFLOPS) against 3.7 minutes; DGEMM 512: 613x; cuRAND,
  ten million numbers: 0.21 ms against 127 ms (612x); nrm2 of ten million: 223x; `solve: 2048` (cuSOLVER's LU and
  getrs against Gaussian elimination in Smalltalk): 6.6 ms against 13.9 s (2,113x, residual 4.6e-4 in float32);
  `fft2d: 2048` (cuFFT, a plan made once, against a radix-2 FFT in Smalltalk): 0.235 ms against 0.9 s (3,848x). ⌘I on a `CudaMatrix` opens the
  Inspector with its device memory, first values and top left corner (`inspectorExtraFields`) and a heat map of up
  to 256 x 256 samples in the theme's colors (`inspectorForm`, `CudaHeatMap`; the Inspector shows it as it shows a
  Form's pixels).
- **cuOpt** (`CuOptWindow`): *Routing*, a depot and stops on a map (click adds a stop, drag moves one or the depot,
  shift-click removes one) and 1–4 vehicles, each visiting at most an even share of the stops plus one. cuOpt's
  routing solver has no C API (C++ and Python only), so `CuOptRouting` states it for the MILP solver: a binary for
  each leg, one leg into and out of each stop, as many out of the depot as back, and Miller-Tucker-Zemlin loads
  against subtours. Ten stops and two vehicles: 120 variables, 113 constraints, optimal in 0.6–0.9 s; the window
  gives cuOpt 1 s (14 stops and 3 vehicles reach it, answering the best found). *Linear program*: the program as
  text (`CuOptProgram`: `maximize 3 chairs + 5 tables`, `wood: chairs <= 4`, `integer`/`binary`/`free` lines),
  solved 0.6 s after typing pauses, the variables and the constraints' activity, bound and slack beside it; four
  examples. An LP takes 13–25 ms; even a five-variable knapsack MILP takes cuOpt 1.5–2 s (its MIP heuristics run in
  time slices). `CuOpt solve:...types:timeLimit:` is the general call.
- **GPU Monitor** (`GpuMonitor`): the device's memory (`cudaMemGetInfo`; on the GB10 `free` is the system's),
  this VM's device memory and handles from the binding's tables (`CudaLibraryAPI allocations`: the `cuda_allocations`
  export, base and size of every live allocation, matched to the `CudaArray` holding it, `CudaArray liveArrays`),
  the bindings' calls by C function, the recent operations with their shapes and the device's time by CUDA events,
  and the device's share of each second spent on them. Its data is `CudaTrace`, on while a monitor is open:
  System-CUDA's operations (products, fills, copies, norms, axpys, cuOpt solves) record themselves, and
  `CudaLibraryAPI check:in:` counts every call; off, a traced operation costs a class variable's test.
  `CudaTrace quietly:` keeps a tool's own reads (the Inspector's, the monitor's) out of it. No utilization from NVML
  yet: the share shown is of traced work.
- **Spectrum** (`SpectrumWindow`, `CudaSpectrum`): a picture (letters, a zone plate, checks, bars; 128, 256 or 512
  square), its two-dimensional DFT on the GPU, the log magnitude spectrum, and the picture again from the spectrum
  through a low-, high- or band-pass filter whose circle one drags on the spectrum. Two engines, a toggle: cuFFT
  (real-to-complex and complex-to-real plans of the half spectrum, made once; the rest of the spectrum by its
  symmetry) or the transform as matrix products on cuBLAS, Y = F X F with F = C - iS, six real products forward and
  six back. The mask is applied on the host, where the spectrum is read anyway. 256 x 256, warm: cuFFT 0.08–0.18 ms
  forward and 0.15 ms back, the cuBLAS DFT 0.11 ms forward (1.5 ms while the GPU's clocks are low), then 3–5 ms of
  copies and Smalltalk work, against 11–15 ms for a radix-2 FFT in Smalltalk (512: 50 ms). The two engines' spectra
  agree to 1e-4 and each round trip is exact to 1e-6.

cuOpt solves on a thread of its own, so the World goes on while it does (seconds for an integer program):
`cuda_cuopt_solve_start` checks the problem's and settings' handles, pins them (the VM refuses them to every call
until the job ends) and runs `cuOptSolve` on a detached thread; `cuda_cuopt_solve_poll` answers 0 while it runs,
then cuOpt's status and the solution's new handle, made on the VM's thread (`CuOpt solveProblem:settings:` polls
every 4 ms; interrupted, it waits for the job and frees the solution). A spec flag `async` for any long call is the
general form of the same (`The next libraries`, Asynchrony). Tests:
`CudaShowcaseModelTest` (Tests-CUDA) and `GpuToolsTest` (Tests-Tools-CUDA, the windows with `GpuTools forced:
false`) in test-core; `CudaShowcaseGpuTest` and `GpuToolsGpuTest` in `make test-nv`.

## NvCompute and libcuda

Where NVIDIA's CUDA userspace is (hosted with the driver, the appliance with the CUDA root below), NvCompute's kernels
run on libcuda; System-NV's RM path stays for machines without it, and for the GPU knowledge it documents (docs/nv.md).
`NvComputeGPU class>>backend` chooses: `SAMALTAK_NV_COMPUTE` (`cuda`, `rm`) if set, else libcuda where it and the
runtime load and see a device, else RM. Both backends have one protocol, so NvComputeGPU and the NV fragment shaders
run unchanged above them:

| | RM (System-NV) | libcuda (System-CUDA) |
| --- | --- | --- |
| device | `NvDevice`: its own RM client, VA space, channel | `NvCudaDevice`: the runtime's primary context on device 0 |
| memory | `NvMemory`: RM system memory mapped for both | `NvCudaMemory`: `cudaMallocHost`, one address for both, a CUDA allocation the VM knows |
| launch | `NvCompute`: QMD and constant bank 0 built per launch | `NvCudaCompute`: `cuModuleLoadData` once a cubin, `cuLaunchKernel` with the parameter area as one buffer |
| fences | semaphore releases on the channel | `cuStreamWriteValue64` of a word the CPU polls, written when a fence is first asked about |
| timestamps | timestamp releases | a one-thread PTX kernel writing `%globaltimer` (compiled by the driver once, 18 ms) |
| L2 flushes | host MEM_OPs | nothing: CUDA keeps the CPU coherent |

The cubins are the same: the precompiled raster kernels (`NvRasterKernels`), NVRTC's shaders, the test kernels;
`NvKernel>>cubin` keeps the bytes the driver loads. Everything is on the default stream of the runtime's primary
context, the one cuBLAS, cuRAND and `CudaArray` use: a kernel and a cuBLAS call on the same memory are ordered on the
device, no host copy, no wait between. `Cuda compute` is the session's `NvCudaCompute`, `Cuda kernelNamed:source:`
compiles a kernel from a String with NVRTC for this device (its cubin kept by the source's SHA-256 in `Cuda
compiler`, an `NvRtcCache`, as NvShaderCompiler keeps the shaders'; element-wise expressions write theirs: see above); a `CudaArray` is a kernel argument as it is:

```smalltalk
| k a |
k := Cuda kernelNamed: 'hilbert' source: 'extern "C" __global__ void hilbert(float *a, int n) {
	int i = blockIdx.x * blockDim.x + threadIdx.x; if (i < n * n) a[i] = 1.0f / (i / n + i % n + 1); }'.
a := CudaMatrix rows: 48 cols: 48.
Cuda compute launch: k grid: 48 * 48 + 255 // 256 block: 256 arguments: {a. 48}.
(a * a) asRows                    "cuBLAS after the kernel on the same stream (NvCudaComputeTest>>testNvrtcKernelThenCublas)"
```

The bindings (spec lines, `tools/cuda/bindgen.py`): `cuModuleLoadData` gets only a whole CUDA ELF (headers, sections
and segments inside the ByteArray) or NUL-terminated PTX (`cudalib_module_image_ok`), anything else is refused before
the driver reads it; `cuModuleGetFunction`'s function handles remember their module and go with it at
`cuModuleUnload` (`free:CUfunction`); `cuLaunchKernel`'s `extra` is a ByteArray (role `params`); `CUstream` is the
runtime's `cudaStream_t` handle type (`alias`), so one stream id serves both libraries; `cudaMallocHost`'s memory is
a live allocation like `cudaMalloc`'s. Not checked, as in C: the addresses a kernel's parameters hold and what its code
does with them (the RM path's kernels reach only what is mapped in its VA space; libcuda's, on the GB10, the process).

Numbers (GB10, `--jit opt`, `NvGpuMeasure report`; then the World on the appliance's screen path, `SAMALTAK_GPU=nv`
`SAMALTAK_SCREEN=memory:1920x1080` under Xvfb, medians of 40 frames, two runs each):

| | RM | libcuda |
| --- | --- | --- |
| fence round trip | 6 µs | 4 µs |
| launch one block and wait | 7 µs | 7 µs (C: 5.2 µs with `cuStreamSynchronize`) |
| queued launches | 2.6 µs each | 2.1 µs each (C: 1.8 µs) |
| copy16, 64 MB | 250 GB/s | 249 GB/s |
| World live frame (nothing changed) | 0.12-0.25 ms | 0.22-0.26 ms |
| World composite (whole screen) | 1.38-1.44 ms (GPU 1.15-1.25) | 1.52-1.55 ms (GPU 1.31-1.37) |
| World redraw (every window again) | 1.71-1.78 ms (GPU 1.43-1.45) | 1.84-2.00 ms (GPU 1.64-1.80) |

A launch costs the same either way; a frame of about 30 launches is 5-10 % slower on libcuda, all of it GPU time
between the stamps: RM's textures are cached in the L2 without coherence (flushed and invalidated by hand), CUDA's
pinned memory is coherent with the CPU. Interop between the RM path and CUDA stays where it was: host copies.

## The World with the cu* libraries: the Linux appliance (the Spark)

One World, the Linux appliance on the Spark (docs/linux-appliance.md), with NVIDIA's CUDA userspace and the cu*
libraries, so the demos above run on bare metal with nothing of DGX OS but its disk. Done: the initramfs stays as it
was (it boots the World in 1-2 s and is what the UKI verifies) and one read-only squashfs, the **CUDA root**, is
mounted at `/opt/cuda` beside it.

    make linux-appliance-cuda          # OUT/linux-appliance/samaltak-cuda-13.squashfs (needs LINUX_GPU=nvidia's modules once)
    make linux-appliance-cuda-test     # QEMU, no GPU: mounted, the libraries load, "no device" as CudaErrors, the VM goes on
    make linux-appliance-cuda-check    # this machine's GPU: the appliance's root + the squashfs by chroot (sudo), the GPU tests
    make linux-appliance-usb           # the stick carries it as a third partition when it is there

**What is in it** (`tools/linux-appliance/cuda.sh`; sizes raw, the squashfs zstd -15 with 1 MiB blocks):

| part | libraries (from) | MB raw |
| --- | --- | --- |
| driver userspace, `nvidia.ko`'s version (580.178.04) | libcuda, libnvidia-ptxjitcompiler, libnvidia-nvvm (the build host's `libnvidia-compute-580`) | 200 |
| CUDA core | libcudart, libcublas, libcublasLt (600 MB alone), libcurand, libnvrtc + builtins, libnvJitLink (the toolkit, 13.0.3) | 984 |
| the next libraries | libcusolver, libcufft, libcusparse (the toolkit) | 582 |
| cuOpt | libcuopt_mathopt, libcuopt_client, RMM, rapids_logger, cuDSS, NCCL, vendored OpenMP/TBB/c-ares (the cuOpt venv's wheels, 26.10) | 550 |
| **total** | 25 files | **2327 MB raw, 1629 MB squashfs** |

zstd -19 saves 2% (1599 MB) for four times the build (36 s instead of 10 s on 8 threads). RAFT is not in it:
libcuopt_mathopt uses it header-only and never loads libraft.so. The tree is `lib/` (each library under its file
name, with links for its soname: one directory), `LICENSES/`, `MANIFEST` (the versions, each file's sha256 and where it
came from: driver package, toolkit or wheel) and a `README`. The build is reproducible: owners, times
(`SOURCE_DATE_EPOCH`, default 0) and xattrs fixed, so the same inputs give the same bytes (two builds, one sha256),
and an unchanged MANIFEST keeps the file.

**Versions, checked by the build.** The driver's three libraries must be `nvidia.ko`'s version: the module the
appliance ships (`linux-modules-nvidia-580-open-<kernel>`, its `modinfo` version) against the build host's
`libcuda.so.<version>`; libcuda refuses a module of another version. The toolkit's CUDA version must be the driver's
major and no newer minor (`cuDriverGetVersion` of that libcuda: 13000; the toolkit 13.0.3), and at least the driver its
`version.json` names. cuOpt's wheel must be the `cu13` one. Everything the libraries need (`NEEDED`, followed
transitively) comes from the set, in that order (toolkit first, then the wheels: one copy of a soname, so cuOpt and the
bindings share one libcublas and libcusparse), or is the system's, which the appliance's root has (glibc and its
compatibility stubs, libstdc++, libgcc_s, zlib, OpenSSL: build.sh now copies libdl, libpthread, librt and libz too).
The toolkit rather than the 13.5 wheels: it is what the bindings were built and measured against, the driver's own
CUDA version (NVRTC's PTX is one the driver's JIT takes), and installed here, so the build downloads nothing. cuOpt's
13.5-built libraries run against it (the GPU tests below; its cuDSS threading layer keeps its own vendored
libcudart 13.3 under another soname).

**Mounting.** `rcS` mounts it after the data volume, from the first of: `samaltak.cuda=UUID=...:/path` on the kernel
command line (a file on that file system: install.sh's boot option names
`/var/lib/samaltak/samaltak-cuda-13.squashfs` on DGX OS's root, already mounted at `/host` for the data volume),
`samaltak.cuda=DEVICE`, the partition named `SAMALTAK-CUDA` (the stick's: the partition is the squashfs), or
`samaltak-cuda-13.squashfs` next to the data volume's image file or on the data volume. The console says
`samaltak-linux: cuda on ... (driver 580.178.04) at 0.29 s`, and warns when the MANIFEST's driver is not
`/sys/module/nvidia/version`. `samaltak-run` then sets `SAMALTAK_CUDA_LIBS=/opt/cuda/lib` and adds it to
`LD_LIBRARY_PATH` (for what the libraries load themselves: libcudart's libcuda, NVRTC's builtins, cuOpt's RMM and
cuDSS); `rcK` unmounts it. Without it the World boots as before, `Cuda isAvailable` false.

**Boot time and size.** Squashfs is read lazily: the mount takes about 10 ms, the World is on the screen as fast as
without it (QEMU: 1.29-1.43 s with the CUDA root, 1.16 s without, the same run of the machine), and the first use pages
in what it touches: loading all five bindings' libraries from the squashfs took 0.44 s under QEMU (cuOpt's 290 MB
library and cuBLASLt most of it). The stick grows by the squashfs (2.9 GB: ESP 224 MB, data 1 GB, CUDA 1.6 GB);
the NVMe install puts 1.6 GB in `/var/lib/samaltak`, nothing more on the ESP.

**Without a GPU** (`make linux-appliance-cuda-test`, QEMU, the NVMe layout: a disk as install.sh leaves DGX OS's root,
the boot option's command line): every binding's library loads from `/opt/cuda/lib`; `cudaGetDeviceCount: cudaErrorNoDevice (no CUDA-capable device is detected)`, `cuInit: CUDA_ERROR_NO_DEVICE`; `Cuda summary` answers `no CUDA here:
cudaGetDeviceCount: cudaErrorNoDevice (...)` (`Cuda unavailableReason`); `cublasCreate` fails with
`CUBLAS_STATUS_NOT_INITIALIZED`, a CudaMatrix with `cudaMalloc: cudaErrorNoDevice`, cuOpt's solve with
`CUOPT_VALIDATION_ERROR`, all CudaErrors; NVRTC (13.0) compiles a kernel to a 5 KB cubin in 0.19 s (no GPU needed);
the VM goes on and the quit powers off. `make linux-appliance-usb-test` checks the stick's partition the same way.

**On this machine's GPU** (`make linux-appliance-cuda-check`): the appliance's root (`OUT/linux-appliance/root`, as
the initramfs holds it) read-only with the squashfs loop-mounted at `/opt/cuda`, `/proc`, `/sys` and `/dev` bound in,
in a private mount namespace (sudo; the mounts and the loop device go with it), and the appliance's VM and image run
in it by `chroot` as the calling user, against the host's `nvidia.ko`. Nothing else of the host is visible, so
every library comes from the root or the squashfs: the loader (`LD_DEBUG=files`) initialized 32 objects, 17 of them
from `/opt/cuda/lib` (libcuda, libcudart, cuBLAS/cuBLASLt, cuRAND, cuSPARSE, nvJitLink, cuOpt and its
dependencies). `CudaGpuTest` 12/12 and `CuOptGpuTest` 4/4 passed; `CudaBenchmark report`: the 4096 SGEMM at
**18.75 TFLOPS** (7.33 ms a product), 1024 at 15.6 TFLOPS, the same as hosted.

**How the World reaches the demos.** The World is the image: the demos are Smalltalk, run from a Workspace or the
Inspector, in the appliance as hosted, one click away in the World menu's Apps › GPU (The GPU demos in the World,
above; `Cuda summary`, `CudaBenchmark report`, a `CudaMatrix`, the cuOpt LP); the
agent can run them too. `make test-nv` on the appliance (or `CudaGpuTest`, `CuOptGpuTest` from the World's test
runner) checks the set. The Spark's first boot with it: docs/linux-appliance.md, section 7.
