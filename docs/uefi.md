# The VM on UEFI

**Scope.** The UEFI app is for QEMU, for machines without a usable Linux, for exploring the firmware (PCI, ACPI, the memory map, from the Debugger) and for a system that is Smalltalk to the metal, with the drivers it has (virtio, e1000e, the firmware's SNP, Block I/O, GOP and HID); no new hardware drivers go into it. The DGX Spark runs Samaltak as the Linux appliance instead (docs/linux-appliance.md: Linux's drivers, the GB10 through `nvidia.ko`, the World on the image's own KMS screen); its GSP boot from UEFI was dropped (docs/nv-gsp.md, archived).

The VM runs as a UEFI application on x86-64 and arm64, with its UI on the firmware's screen: no operating system, no C library, no hand-written C, no file system. It is translated from the same Lowtalk as `vm/gen`, with the `VM-UEFI` package in place of the C library and the OS. The image is everything there is (sources, fonts) and lives on a raw partition.

    make uefi                                       # $(OUT)/uefi-$(UEFI_ARCH)/esp: a boot volume; .../image.disk: the image
    make uefi-run UEFI_ARGS="--headless --eval '3 + 4'"   # boot it in QEMU with its UEFI firmware; fails unless the VM exits 0
    make uefi-ui                                    # the World in a QEMU window (macOS: UEFI_SCREEN points, in front; needs Accessibility)
    make uefi-ui UEFI_DISPLAY=1 UEFI_GPU=virtio-gpu-pci UEFI_SCREEN=1920x1080   # on the image's own VNC (RFB) server on 127.0.0.1:5901 instead, QEMU without a display (password: ~/.samaltak-vnc where present; docs/remote.md, Remote display)
    make uefi-ui UEFI_VNC=1 UEFI_GPU=virtio-gpu-pci UEFI_SCREEN=1920x1080   # on QEMU's VNC server on 127.0.0.1:5901, the fallback (password: ~/.samaltak-vnc)
    make uefi-control UEFI_CONTROL_PORT=7341        # no window; its control service on 127.0.0.1:7341 (samaltak-ctl open --uefi; token: docs/remote.md)
    make test-uefi                                  # the tests that need no platform layer, the World, the network, a snapshot: its parts boot at once (UEFI_TEST_JOBS), each in $(OUT)/uefi-$(UEFI_ARCH)/run-<part> (UEFI_RUN), kept when one fails
    make uefi-control UEFI_AFFINITY=5-8             # QEMU on these host CPUs (the World's default: big; Pinning)

`UEFI_ARCH` is `x86_64` or `arm64`, this machine's by default. Needs clang, ld.lld, `qemu-system-x86_64` or `qemu-system-aarch64` and the firmware for it, OVMF or AAVMF (`.agents/setup` installs x86-64's; Homebrew's `qemu` has both). For this machine's CPU QEMU runs the VM on it, with KVM where `/dev/kvm` is there, else on macOS with Hypervisor.framework (QEMU 11.0 fails at its start on macOS 26; 11.1 works); for another CPU it emulates (TCG), and the VM still boots in about 5 s.

## How

- **Translation.** `VMTranslator generateVMInto: dir os: #uefi arch: #x86_64` (or `#arm64`) translates the core's modules for every OS and `VM-UEFI`'s (docs/lowtalk.md, An OS without a C library): `UefiLibC`, `UefiLibM` and `UefiPosix` implement `LibC`, `LibM` and `Posix`; `UefiTicker`, `UefiJitPlatform` and `UefiPlatform` the core's `Ticker`, `JitPlatform` and `PlatformInterface`. The platform primitives are `PlatformPrimitives` as everywhere, over VM-UEFI's modules in place of the SDL and POSIX ones: `UefiMachine` (the firmware for the machine primitives), `UefiSnp` (the raw network interface), `UefiNoDisplay` for windows, events, the refresh and the GPU, and `UefiNoIO` for files, sockets, TLS and ptys, which all fail; the raster primitives are `PlatformRaster`'s, as everywhere. What differs between the CPUs is `UefiCpu`, an arch interface (`UefiX64Cpu`, `UefiArm64Cpu`): the cycle counter, instruction cache maintenance, switching stacks, with the instructions C has no builtin for in their C preambles. Not checked in: `make uefi` translates into `$(OUT)/uefi-$(UEFI_ARCH)/gen`. The C that is not translated (vm/native: stubs on UEFI, no cryptography) is compiled with it.
- **Core FFI.** UEFI does not publish FFI wrappers at runtime. Prepared `vm:core` descriptors for float fraction and printing, wall and thread clocks, and stdout/stderr select statically linked typed wrappers. Each call checks the exact name, signature and arguments; no native address or binding token is stored in the image. UEFI has no dynamic grants or environment. Large Integer arithmetic uses the image implementation.
- **Compiling.** `vm/uefi.mk`: clang for `x86_64-unknown-none-elf` or `aarch64-unknown-none-elf`, freestanding, with the ABI the JIT assumes (on x86-64 System V); the firmware's functions are called through `ms_abi` function types (`UefiModule>>efi:with:...`), and `efi_main` and the timer's notification function are `ms_abi` (`<abi: 'ms_abi'>`): UEFI's convention on x86-64, nothing on AArch64, where UEFI's is the standard one. `ld.lld` links a static PIE; `UefiImageWriter` (Smalltalk) turns it into a PE32+ EFI application: one read-write-execute section (the JIT's code cache is the zero-fill array the VM reserves for it) and base relocations.
- **Boot volume.** FAT, as the firmware requires: `EFI/BOOT/BOOTX64.EFI` (`BOOTAA64.EFI`) and `samaltak.args`, the command line, one argument a line (without it: `disk: --headless`).
- **The image on disk.** `UefiImageStore`: a raw partition or disk that starts with its superblock (found among the firmware's block devices), two slots of image. The image path `disk:` reads the newest slot; a snapshot writes the other, flushes, then writes that slot's header with the next sequence number, so a crash while saving leaves the last good image. `UefiImageDisk` (Smalltalk) writes a store with the image in slot 0; `make uefi` extends it to `UEFI_DISK_MB` (512). Slots are half of what follows the first megabyte: the partition must be at least twice the image plus 1 MB.
- **Devices in the image.** The VM has no display, input or network drivers: the image drives them (`System-Devices`, layer 0) through the machine primitives (`Machine`: memory by address, memory outside the heap, firmware calls in its convention, its events signaling Semaphores; docs/platform.md), with the firmware's boot services and protocols (`Firmware`). `GPUPlatform` (Graphics-GPU) chooses its backends when the image starts: where the VM has no firmware the VM's primitives (`GPUPrimitives`), here `FirmwareDisplay` for windows and events and a `SoftwareGPU` on it (`--gpu nv` would put an `NvComputeGPU` there once System-NV runs on UEFI: docs/nv-gpu.md). All of it is Smalltalk, editable while it runs.
- **Display.** `FirmwareScreen`: the firmware's graphics output (GOP) in its mode of the size the World opens with (`--window-size`; `make uefi-ui` passes `UEFI_SCREEN`, 1024x768), else the mode it booted with (1280×800 on OVMF), drawn straight into its linear framebuffer, or with the protocol's `Blt` from the shadow copy where the mode has none (PixelBltOnly: edk2's VirtioGpuDxe). `UEFI_GPU` picks QEMU's display device: arm64's default `ramfb` has modes up to 1024x768, `virtio-gpu-pci` (no framebuffer, so `Blt`) up to 1920x1080 and beyond, x86-64's standard VGA up to 1920x1080 and more; `make test-uefi` opens the World at 1920x1080 on `virtio-gpu-pci` too. `UEFI_DISPLAY=N` shows `uefi-ui` or `uefi-control` on the image's own VNC server (RFB, docs/remote.md) on 127.0.0.1:590N, and `UEFI_VNC=N` on QEMU's (the fallback; its password the file `UEFI_VNC_PASSWORD`, `~/.samaltak-vnc`, at most 8 characters, which `UEFI_DISPLAY` takes too where present) instead of a window, for a machine reached over ssh: `ssh -L 590N:127.0.0.1:590N`, then `vnc://localhost:590N` (`samaltak-ctl open --uefi --vnc N` uses the image's server, `--vnc-server qemu` QEMU's); one window, the screen, at one pixel a point (`FirmwareDisplay`); the pointer is an arrow drawn over a shadow copy of the frame, moved without a new frame. Once it draws, the firmware's text console is silenced (its OutputString becomes its TestString). `SoftwareGPU` renders in software: the device (handles, textures and buffers in memory outside the heap, passes, command buffers, the swapchain, fences) is Smalltalk; the pixel work is the raster primitives (`PlatformRaster`, the same on every OS): the Renderer's uber-shader (every mode: solid, glyphs, images, halftone, stripes, lines) with row fast paths for axis-aligned quads, premultiplied blending, blits, copies; the swapchain is a BGRA8 back buffer that `submit` presents. It runs no other shader: a `FragmentShader` (ShaderView, the juggler) shows its error. On a software device (`GPUDevice>>isSoftware`) the Compositor composes only when something changed and rests after each frame as long as it took, so that the other Processes keep at least half of the CPU.
- **Input.** Drivers in Processes at priority 75, above the compositor: `FirmwareKeyboard` (the firmware's extended text input, read whenever the firmware signals its key event: a key stroke is keyDown, textInput, keyUp; Alt is cmd as on Linux), `VirtioInput` (a virtio tablet or mouse through the firmware's PCI I/O, its virtqueue (`Virtqueue`) in the device's DMA memory polled every 10 ms, for firmware without a pointer driver: OVMF has none), else `FirmwarePointer` (the firmware's absolute or simple pointer, read when it signals). `InputQueue` makes and queues the events as the VM's queue does elsewhere, with remote control's injected ones (`RemoteInputDevice`); `RefreshClock` signals the compositor's semaphore at 60 Hz.
- **Network.** The image drives the NIC and does TCP/IP. Its drivers (`PciNetworkInterface`, System-Devices) are for QEMU's standard NICs: `E1000eInterface`, the Intel 82574L (e1000e, the default on q35 and `make uefi-run`'s on x86-64), and `VirtioNetInterface`, virtio-net (virtio 1.x over `VirtioPci`, its queues `Virtqueue`s; the default on arm64 `virt` and `make uefi-run`'s there). `NetworkInterface open` starts the first controller among the firmware's PCI devices that one of them supports: it takes it from the firmware's drivers (DisconnectController, the controllers they made first: VirtioNetDxe with MNP and everything over it, iPXE from an option ROM; `make uefi-run` gives QEMU's NICs none), resets it and drives it on its registers in its memory BARs, its rings and buffers in DMA memory from the PCI I/O protocol. No interrupts: the stack's Process takes the frames when it wakes, at least every 10 ms, and a Process of the driver's, just above the idle Process, wakes it sooner when a frame is there: for 1 ms after a frame went out, until one comes, it looks without pause (the answer, an ACK, is due); otherwise, while frames came or went in the last 100 ms, at every tick of the firmware's timer, which then ticks every millisecond (`Firmware>>fineTicks:`: `EFI_TIMER_ARCH_PROTOCOL`'s SetTimerPeriod; a timer event of the driver's, watched, at each tick), the CPU halted in between. (It looked without pause for 20 ms after every frame before: most of a vCPU while anyone typed over the network.) Without a controller the image supports, the VM's NIC: `UefiSnp` (in place of `PlatformNic`: the `nic*` primitives, docs/platform.md) drives it through the firmware's simple network protocol, opened exclusively so that the firmware's own network stack (MNP and everything over it) lets go of it; it moves what the NIC received into a queue at the platform's polls, every millisecond while the image waits for frames; as with the image's drivers, a wait polls it without pause for 1 ms after a frame went out until one comes, and while frames came or went in the last 100 ms the firmware's timer ticks every millisecond (`UefiMachine>>fineTicks:`) and a wait lasts until its next tick (without the timer protocol, it polls without pause for 20 ms, as before). The socket primitives fail (`UefiNoIO`); `RemoteSocket` uses the image's stack instead (`NetworkStack active`, System-Network), started on first use: Ethernet, ARP (a cache with aging), IPv4 (to the gateway unless for the subnet; fragments dropped; 127/8 loops back), ICMP (it answers ping), UDP, a DHCP client (renewing the lease), a DNS resolver (A records, CNAMEs, the servers DHCP gave), and TCP (`TcpConnection`, RFC 9293: active and passive opens with a backlog, the MSS option, windows both ways (at most 64 KB: no window scaling), out-of-order segments kept until the gap fills, an RTO per RFC 6298 (Karn; at least 200 ms), fast retransmit and NewReno recovery, slow start and congestion avoidance, delayed ACKs, zero-window probes, RSTs only at the exact sequence number (RFC 5961), every closing state, a TIME_WAIT of 2 s), in a Process of its own at priority 55. So ControlServer, `HTTPClient` (no TLS: no HTTPS; the appliance has it, docs/linux-appliance.md) and the rest work unchanged. `--control-host 0.0.0.0` lets the control service listen on every address, which `make uefi-control` does in the guest behind QEMU's user network, and forwards the host's `127.0.0.1:UEFI_CONTROL_PORT` to; `samaltak-ctl open --uefi` runs it, and its screenshots come back in the response. Every request needs the service's token (docs/remote.md): `open --uefi` hands its session's to `make uefi-control` in the environment (`UEFI_CONTROL_TOKEN`), which writes it into `samaltak.args` (`--control-token`, mode 0600); without one the image makes one and shows it on the console. Under QEMU's user network without KVM: 1.5 ms from Smalltalk to an echo server on the host and back; 16 MB from the host in about 0.85 s (e1000e) or 1.3 s (virtio-net), to it in about 1.65 s (either; through the firmware's SNP 0.85 s and 1.9 s with iPXE's e1000e driver, 1.4 s and 1.75 s with VirtioNetDxe).
- **Entropy.** `SecureRandom` (System-Crypto, docs/crypto.md) seeds from the firmware's `EFI_RNG_PROTOCOL` (GetRNG, its default algorithm). QEMU's AAVMF offers it only over a virtio-rng device (OVMF too unless it has RDRAND's), so QEMU_UEFI adds one (`-device virtio-rng-pci`); where the firmware has none, SecureRandom signals CryptoError rather than answer weaker randomness. With no cryptography on UEFI (System-Crypto's operations signal CryptoError 'no crypto on UEFI') SecureRandom answers the firmware's bytes directly, health-checked (docs/crypto.md, Randomness).
- **Firmware services.** `UefiFirmware` (`efi_main`): first makes its image writable and executable where the firmware protects it by its sections (edk2 on AArch64 maps the one section read-only; `EFI_MEMORY_ATTRIBUTE_PROTOCOL`, which ArmVirtQemu uninstalls, else the CPU architectural protocol's `SetMemoryAttributes`), turns off the boot manager's watchdog, switches to a stack of 8 MB (the firmware's is 128 KB; the JIT's code keeps a native frame per activation), opens the volume, runs `VMMain`, and powers off with the exit status (`samaltak: exit N` on the console). `Firmware powerOff`, `restart` and `warmRestart` (the World menu's System › Power off, Restart, Warm restart) run the shutdown list as quitting does, then the firmware's `ResetSystem` (`samaltak: reset shutdown|cold|warm`; QEMU with `-no-reboot` exits on a reset). Console output goes to the serial port if there is one, else to `ConOut` (silent once the image draws on the screen). Memory: `malloc` is the firmware's pool, `mmap` its pages (zeroed). Time: the cycle counter (`rdtsc`, `cntvct_el0`), calibrated against `Stall`; the wall clock is `GetTime` at start plus that. Timers: timer events whose notification calls `Scheduler>>tickFired:` (OVMF's timer ticks every 10 ms; every millisecond while the NIC is busy, above). Idle: `WaitForEvent` on a timer and the events the image watches (`UefiMachine`), which halts the CPU.

## Crash reports

In the image, a Notifier's or Debugger's **Save report** button writes `samaltak-crash-<n>.txt` for the stopped Process (`CrashReport`, System-Debugging) to `~/.local/state/samaltak`, which needs an operating system's files: on UEFI it fails. A fatal error of the VM is said on the console (`samaltak: fatal: ...`, the Smalltalk stack), then the VM powers off with status 70.

## Pinning

On a machine with two kinds of core QEMU should run on the fast ones. The DGX Spark has ten Cortex-X925 (3.9 GHz: CPUs 5-9 and 15-19) and ten Cortex-A725 (2.8 GHz, about half as fast for the VM); Linux places a thread by how busy it has been, so the vCPU of an idle World wakes on an A725 for each burst of work (a frame, a key, an evaluation) and only a long computation moves it to an X925.

`UEFI_AFFINITY` says where QEMU runs (`tools/qemu-pin.sh`): `big`, the cores of the highest `cpuinfo_max_freq` (Linux, where there is more than one kind; elsewhere unpinned), a `taskset` list such as `5-9,15-19`, or empty or `none`, anywhere. Pinned, QEMU runs under `taskset -c` with its threads named (`-name samaltak,debug-threads=on`), `-smp` is cut to the cores of the list, and each vCPU thread (`CPU n/KVM`) is pinned to a core of its own, the least busy of the list as QEMU starts; the other threads (the main loop, which does virtio-gpu's transfers, I/O) stay on the list. Its log line says where: `qemu-pin: QEMU on CPUs 5,6,7,8,9,15,16,17,18,19; vCPU 0 on 6, vCPU 1 on 7, ...`. The World (`uefi-ui`, `uefi-control`, so `samaltak-ctl open --uefi`, which also takes `--affinity` and `--cpus`) runs on `big` unless `UEFI_AFFINITY` is set; `uefi-run`, `uefi-boot` and the tests stay unpinned, as gates run at once and would crowd onto the same few cores. `samaltak.vncWorld` opens the operator's World with `big` and 4 vCPUs.

Measured (the World at 1920x1080 on `virtio-gpu-pci`, 4 vCPUs, the machine shared with other agents, load about 2): 25 times fib(25) after 150 ms idle, as a click or a key does, 0.90 ms pinned against 0.93 to 1.5 ms unpinned (the median of a run: an A725); a re-rendered frame 3.5 to 3.7 ms pinned, 3.3 to 5.2 ms unpinned; on the A725s alone (`UEFI_AFFINITY=0-3`) fib(32) under the JIT 44 to 51 ms against 27, and a frame 5 ms. A long computation unpinned soon runs on an X925 (fib(32) 27 to 29 ms either way).

## Limits

- No files from Smalltalk, processes or ptys; no shaders but the Renderer's. No TLS (so no HTTPS) and no cryptography: those are the Linux appliance's (docs/linux-appliance.md).
- The network: one NIC (the first the image has a driver for, else the firmware's first Ethernet one), IPv4 only, no IP fragments, multicast or IP options sent; TCP without window scaling, SACK, timestamps or keepalives.
- Software rendering: a typical 1280×800 frame takes about 4 ms natively, 100 ms or more under QEMU without KVM.
- Memory is physical: the heap's reservations (twice `--max-heap` plus the young space) are allocated and zeroed at start. `make uefi-run`, `uefi-boot` and `test-uefi` pass `--max-heap 256` and give QEMU 2 GB; the World (`uefi-ui`, `uefi-control`, so `samaltak-ctl open --uefi`) gets `--max-heap 1024` in 4 GB (`UEFI_WORLD_HEAP_MB`, a quarter of `UEFI_WORLD_RAM_MB`). `UEFI_HEAP_MB` and `UEFI_RAM_MB` override both. A quarter, because the heap takes twice its limit and the rest of the RAM is for the firmware, the VM and what the image keeps outside the heap: the SoftwareGPU's textures (a Form shown at 1920x1080 is 8 MB there too), the back buffer and the drivers' buffers. Measured at 1920x1080 on arm64: the idle World uses 57 MB of heap; each screenshot an agent shows was 8.4 MB more until the conversation kept only its newest four (docs/agent.md, Images). With 1 GB in 4 GB 1.7 GB stay free outside the heap; 768 MB in 2 GB left 144 MB. Near the limit the VM signals `OutOfMemory` or `StackOverflow` rather than dying (docs/implementation.md, Primitive interface); `LowSpaceTest` boots in a 128 MB heap in `test-uefi`.
- One CPU, the firmware's timer resolution, its block device drivers.

## Real hardware

On a USB stick: a FAT32 partition with the contents of `$(OUT)/uefi-$(UEFI_ARCH)/esp`, and a second partition of at least twice the image plus 1 MB with `image.disk` written to its start (`dd`). Boot it on a UEFI PC (or arm64 machine) with Secure Boot off. The pointer needs the firmware's USB mouse driver (most PC firmware has one; OVMF does not). The network needs an Intel 82574L or a virtio-net, else a NIC the firmware (or its option ROM) has a driver for: the VM's `UefiSnp` drives the firmware's first simple network protocol.

The DGX Spark runs the Linux appliance (docs/linux-appliance.md: its own USB stick, `make linux-appliance-usb`, and an installer next to DGX OS). The bare-metal boot image, firmware diagnostics and installer the fork had for it are kept only at the tag `archive/uefi-bare-metal`.
