# The VM on UEFI

The VM runs as a UEFI application on x86-64 and arm64, with its UI on the firmware's screen: no operating system, no C library, no hand-written C, no file system. It is translated from the same Lowtalk as `vm/gen`, with the `VM-UEFI` package in place of the C library and the OS. The image is everything there is (sources, fonts) and lives on a raw partition; the machine's ext4 volumes are its files, read-only (docs/files.md).

    make uefi                                       # $(OUT)/uefi-$(UEFI_ARCH)/esp: a boot volume; .../image.disk: the image
    make uefi-run UEFI_ARGS="--headless --eval '3 + 4'"   # boot it in QEMU with its UEFI firmware; fails unless the VM exits 0
    make uefi-ui                                    # the World in a QEMU window (macOS: UEFI_SCREEN points, in front; needs Accessibility)
    make uefi-ui UEFI_VNC=1 UEFI_GPU=virtio-gpu-pci UEFI_SCREEN=1920x1080   # on a VNC server on 127.0.0.1:5901 instead (password: ~/.samaltak-vnc)
    make uefi-control UEFI_CONTROL_PORT=7341        # no window; its control service on 127.0.0.1:7341 (samaltak-ctl open --uefi; token: docs/remote.md)
    make test-uefi                                  # the tests that need no platform layer, the World, the network, a snapshot
    make usb-image                                  # $(OUT)/uefi-$(UEFI_ARCH)/usb.img: a boot disk to dd onto a USB stick (Real hardware)
    make usb-image USB_DIAG=1                       # the same, booting into FirmwareDiagnostics first, then the World
    make usb-image USB_CONTROL=1                    # with the control service on the network, for samaltak-ctl connect (docs/remote.md)
    make test-usb-image                             # boots such a file in QEMU as a USB stick and as NVMe
    make uefi-run UEFI_CPUS=1                       # on one CPU (QEMU's -smp; 4 by default)
    make uefi-control UEFI_AFFINITY=5-8             # QEMU on these host CPUs (the World's default: big; Pinning)

`UEFI_ARCH` is `x86_64` or `arm64`, this machine's by default. Needs clang, ld.lld, `qemu-system-x86_64` or `qemu-system-aarch64` and the firmware for it, OVMF or AAVMF (`.agents/setup` installs x86-64's; Homebrew's `qemu` has both). For this machine's CPU QEMU runs the VM on it, with KVM where `/dev/kvm` is there, else on macOS with Hypervisor.framework (QEMU 11.0 fails at its start on macOS 26; 11.1 works); for another CPU it emulates (TCG), and the VM still boots in about 5 s.

## How

- **Translation.** `VMTranslator generateVMInto: dir os: #uefi arch: #x86_64` (or `#arm64`) translates the core's modules for every OS and `VM-UEFI`'s (docs/lowtalk.md, An OS without a C library): `UefiLibC`, `UefiLibM` and `UefiPosix` implement `LibC`, `LibM` and `Posix`; `UefiTicker`, `UefiJitPlatform` and `UefiPlatform` the core's `Ticker`, `JitPlatform` and `PlatformInterface`. The platform primitives are `PlatformPrimitives` as everywhere, over VM-UEFI's modules in place of the SDL and POSIX ones: `UefiMachine` (the firmware for the machine primitives), `UefiSnp` (the raw network interface), `UefiNoDisplay` for windows, events, the refresh and the GPU, and `UefiNoIO` for files, sockets, TLS and ptys, which all fail; the raster primitives are `PlatformRaster`'s, as everywhere. What differs between the CPUs is `UefiCpu`, an arch interface (`UefiX64Cpu`, `UefiArm64Cpu`): the cycle counter, instruction cache maintenance, switching stacks, with the instructions C has no builtin for in their C preambles. Not checked in: `make uefi` translates into `$(OUT)/uefi-$(UEFI_ARCH)/gen`.
- **Compiling.** `vm/uefi.mk`: clang for `x86_64-unknown-none-elf` or `aarch64-unknown-none-elf`, freestanding, with the ABI the JIT assumes (on x86-64 System V); the firmware's functions are called through `ms_abi` function types (`UefiModule>>efi:with:...`), and `efi_main` and the timer's notification function are `ms_abi` (`<abi: 'ms_abi'>`): UEFI's convention on x86-64, nothing on AArch64, where UEFI's is the standard one. `ld.lld` links a static PIE; `UefiImageWriter` (Smalltalk) turns it into a PE32+ EFI application: one read-write-execute section (the JIT's code cache is the zero-fill array the VM reserves for it) and base relocations.
- **Boot volume.** FAT, as the firmware requires: `EFI/BOOT/BOOTX64.EFI` (`BOOTAA64.EFI`) and `samaltak.args`, the command line, one argument a line (without it: `disk: --headless`).
- **The image on disk.** `UefiImageStore`: a raw partition or disk that starts with its superblock (found among the firmware's block devices), two slots of image. The image path `disk:` reads the newest slot; a snapshot writes the other, flushes, then writes that slot's header with the next sequence number, so a crash while saving leaves the last good image. `UefiImageDisk` (Smalltalk) writes a store with the image in slot 0; `make uefi` extends it to `UEFI_DISK_MB` (512). Slots are half of what follows the first megabyte: the partition must be at least twice the image plus 1 MB.
- **Devices in the image.** The VM has no display, input or network drivers: the image drives them (`System-Devices`, layer 0) through the machine primitives (`Machine`: memory by address, memory outside the heap, firmware calls in its convention, its events signaling Semaphores; docs/platform.md), with the firmware's boot services and protocols (`Firmware`). `GPUPlatform` (Graphics-GPU) chooses its backends when the image starts: where the VM has no firmware the VM's primitives (`GPUPrimitives`), here `FirmwareDisplay` for windows and events and a `SoftwareGPU` on it (`--gpu nv` would put an `NvComputeGPU` there once System-NV runs on UEFI: docs/nv-gpu.md). All of it is Smalltalk, editable while it runs.
- **Display.** `FirmwareScreen`: the firmware's graphics output (GOP) in its mode of the size the World opens with (`--window-size`; `make uefi-ui` passes `UEFI_SCREEN`, 1024x768), else the mode it booted with (1280×800 on OVMF), drawn straight into its linear framebuffer, or with the protocol's `Blt` from the shadow copy where the mode has none (PixelBltOnly: edk2's VirtioGpuDxe). `UEFI_GPU` picks QEMU's display device: arm64's default `ramfb` has modes up to 1024x768, `virtio-gpu-pci` (no framebuffer, so `Blt`) up to 1920x1080 and beyond, x86-64's standard VGA up to 1920x1080 and more; `make test-uefi` opens the World at 1920x1080 on `virtio-gpu-pci` too. `UEFI_VNC=N` shows `uefi-ui` or `uefi-control` on a VNC server on 127.0.0.1:590N (its password the file `UEFI_VNC_PASSWORD`, `~/.samaltak-vnc`, at most 8 characters) instead of a window, for a machine reached over ssh: `ssh -L 590N:127.0.0.1:590N`, then `vnc://localhost:590N`; one window, the screen, at one pixel a point (`FirmwareDisplay`); the pointer is an arrow drawn over a shadow copy of the frame, moved without a new frame. Once it draws, the firmware's text console is silenced (its OutputString becomes its TestString). `SoftwareGPU` renders in software: the device (handles, textures and buffers in memory outside the heap, passes, command buffers, the swapchain, fences) is Smalltalk; the pixel work is the raster primitives (`PlatformRaster`, the same on every OS): the Renderer's uber-shader (every mode: solid, glyphs, images, halftone, stripes, lines) with row fast paths for axis-aligned quads, premultiplied blending, blits, copies; the swapchain is a BGRA8 back buffer that `submit` presents. It runs no other shader: a `FragmentShader` (ShaderView, the juggler) shows its error. On a software device (`GPUDevice>>isSoftware`) the Compositor composes only when something changed and rests after each frame as long as it took, so that the other Processes keep at least half of the CPU.
- **Input.** Drivers in Processes at priority 75, above the compositor: `FirmwareKeyboard` (the firmware's extended text input, read whenever the firmware signals its key event: a key stroke is keyDown, textInput, keyUp; Alt is cmd as on Linux), `VirtioInput` (a virtio tablet or mouse through the firmware's PCI I/O, its virtqueue (`Virtqueue`) in the device's DMA memory polled every 10 ms, for firmware without a pointer driver: OVMF has none), else `FirmwarePointer` (the firmware's absolute or simple pointer, read when it signals). `InputQueue` makes and queues the events as the VM's queue does elsewhere, with remote control's injected ones (`RemoteInputDevice`); `RefreshClock` signals the compositor's semaphore at 60 Hz.
- **Network.** The image drives the NIC and does TCP/IP. Its drivers (`PciNetworkInterface`, System-Devices) are for QEMU's standard NICs: `E1000eInterface`, the Intel 82574L (e1000e, the default on q35 and `make uefi-run`'s on x86-64), and `VirtioNetInterface`, virtio-net (virtio 1.x over `VirtioPci`, its queues `Virtqueue`s; the default on arm64 `virt` and `make uefi-run`'s there). `NetworkInterface open` starts the first controller among the firmware's PCI devices that one of them supports: it takes it from the firmware's drivers (DisconnectController, the controllers they made first: VirtioNetDxe with MNP and everything over it, iPXE from an option ROM; `make uefi-run` gives QEMU's NICs none), resets it and drives it on its registers in its memory BARs, its rings and buffers in DMA memory from the PCI I/O protocol. No interrupts: the stack's Process takes the frames when it wakes, at least every 10 ms, and a Process of the driver's, just above the idle Process, looks for a frame without pause while frames came or went in the last 20 ms and wakes the stack when one is there. Without a controller the image supports, the VM's NIC: `UefiSnp` (in place of `PlatformNic`: the `nic*` primitives, docs/platform.md) drives it through the firmware's simple network protocol, opened exclusively so that the firmware's own network stack (MNP and everything over it) lets go of it; it moves what the NIC received into a queue at the platform's polls, every millisecond while the image waits for frames, and while frames come and go a wait polls it without pause (the firmware's timer ticks every 10 ms). The socket primitives fail (`UefiNoIO`); `RemoteSocket` uses the image's stack instead (`NetworkStack active`, System-Network), started on first use: Ethernet, ARP (a cache with aging), IPv4 (to the gateway unless for the subnet; fragments dropped; 127/8 loops back), ICMP (it answers ping), UDP, a DHCP client (renewing the lease), a DNS resolver (A records, CNAMEs, the servers DHCP gave), and TCP (`TcpConnection`, RFC 9293: active and passive opens with a backlog, the MSS option, windows both ways (at most 64 KB: no window scaling), out-of-order segments kept until the gap fills, an RTO per RFC 6298 (Karn; at least 200 ms), fast retransmit and NewReno recovery, slow start and congestion avoidance, delayed ACKs, zero-window probes, RSTs only at the exact sequence number (RFC 5961), every closing state, a TIME_WAIT of 2 s), in a Process of its own at priority 55. So ControlServer, `HTTPClient` and the rest work unchanged, HTTPS too: `TLSSocket` does TLS 1.3 and 1.2 in Smalltalk where the TLS primitives fail (docs/tls.md). `--control-host 0.0.0.0` lets the control service listen on every address, which `make uefi-control` does in the guest behind QEMU's user network, and forwards the host's `127.0.0.1:UEFI_CONTROL_PORT` to; `samaltak-ctl open --uefi` runs it, and its screenshots come back in the response. Every request needs the service's token (docs/remote.md): `open --uefi` hands its session's to `make uefi-control` in the environment (`UEFI_CONTROL_TOKEN`), which writes it into `samaltak.args` (`--control-token`, mode 0600); without one the image makes one and shows it on the console. Under QEMU's user network without KVM: 1.5 ms from Smalltalk to an echo server on the host and back; 16 MB from the host in about 0.85 s (e1000e) or 1.3 s (virtio-net), to it in about 1.65 s (either; through the firmware's SNP 0.85 s and 1.9 s with iPXE's e1000e driver, 1.4 s and 1.75 s with VirtioNetDxe).
- **Entropy.** `SecureRandom` (System-Crypto, docs/crypto.md) seeds from the firmware's `EFI_RNG_PROTOCOL` (GetRNG, its default algorithm). QEMU's AAVMF offers it only over a virtio-rng device (OVMF too unless it has RDRAND's), so QEMU_UEFI adds one (`-device virtio-rng-pci`); where the firmware has none, SecureRandom signals CryptoError rather than answer weaker randomness.
- **Files.** `FirmwareVolumes` (System-Storage) mounts the ext4 volumes of the firmware's block devices (`FirmwareBlockDevice`: Block I/O, never the image store or its disk, but the other partitions of that disk) read-only for `File`, `FileStream` and `Directory`, the first at `/` and each at `/mnt/<label>` (docs/files.md); `make uefi-run UEFI_DISKS="disk.img@nvme"` attaches a disk image.
- **Firmware services.** `UefiFirmware` (`efi_main`): first makes its image writable and executable where the firmware protects it by its sections (edk2 on AArch64 maps the one section read-only; `EFI_MEMORY_ATTRIBUTE_PROTOCOL`, which ArmVirtQemu uninstalls, else the CPU architectural protocol's `SetMemoryAttributes`), turns off the boot manager's watchdog, switches to a stack of 8 MB (the firmware's is 128 KB; the JIT's code keeps a native frame per activation), opens the volume, runs `VMMain`, and powers off with the exit status (`samaltak: exit N` on the console). Console output goes to the serial port if there is one, else to `ConOut` (silent once the image draws on the screen). Memory: `malloc` is the firmware's pool, `mmap` its pages (zeroed). Time: the cycle counter (`rdtsc`, `cntvct_el0`), calibrated against `Stall`; the wall clock is `GetTime` at start plus that. Timers: timer events whose notification calls `Scheduler>>tickFired:` (OVMF's timer ticks every 10 ms). Idle: `WaitForEvent` on a timer and the events the image watches (`UefiMachine`), which halts the CPU.

## More than one CPU

The VM runs on the boot CPU; the others, the application processors (APs), run only the VM's C for it: parts of the raster's work and the JIT's background compilation. UEFI allows its services on the boot CPU alone, and the heap is the boot CPU's too, so an AP never calls the firmware, allocates or touches the heap.

- **Starting them.** `UefiMp` at start: where the firmware has `EFI_MP_SERVICES_PROTOCOL` (OVMF, and any edk2 with `CpuDxe` or `ArmPsciMpServicesDxe`), `StartupThisAP` of each enabled AP, non-blocking, with a procedure that switches to a stack of the VM's (4 MB) and never returns. Else on arm64 PSCI `CPU_ON` (QEMU's AAVMF has no MP services): the CPUs are the enabled GICC entries of the ACPI MADT, the conduit HVC or SMC as the FADT's ARM_BOOT_ARCH flags say; an AP starts at `UefiArm64Cpu`'s entry stub with its MMU and caches off, at the exception level of the boot CPU (EL1 under KVM, EL2 on bare metal and under QEMU's `virtualization=on`), reads its `MpAp` (cleaned to the point of coherency) and sets up the boot CPU's MMU (MAIR, TCR, TTBR0/1, SCTLR, VBAR; at EL2 HCR too), the FPU (CPACR or CPTR) and its stack before it calls C. The console says how: `samaltak: 4 CPUs (PSCI by HVC at EL1)`, `samaltak: 4 CPUs (MP services)`. Firmware with neither, or `UEFI_CPUS=1`, leaves one CPU, and everything runs on it as before, with the same results.
- **Per-CPU state.** Each CPU has its own block of `_Thread_local` variables (local-exec TLS, its thread pointer TPIDR_EL0 or the FS base): a module's `threadLocalVariables` (docs/lowtalk.md) are thread-local in the UEFI translation only (plain globals elsewhere); `PlatformRaster`'s raster state is. `UefiImageWriter` takes a zero-initialized PT_TLS of at most 4 KB.
- **Work.** `CpuWorkers` (VM-Platform; `UefiCpuWorkers` here, `NoCpuWorkers` elsewhere): a parallel job is a function, its context and a number of parts, published in one word (sequence, count, next part); the boot CPU and every idle AP take the next part with a compare-and-swap of that word (C11 atomics: LDAXR/STLXR or LSE, LOCK on x86-64; acquire and release where the protocol needs them), run it and count it done, and the boot CPU returns when all are. A busy AP (compiling) simply takes no part. An idle AP waits on that word's cache line (WFE on the exclusive monitor and WFET; MONITOR/MWAIT where the CPU has it, else PAUSE) while work came in the last 50 ms, then naps (WFIT where there is FEAT_WFxT: under KVM its vCPU sleeps), so idle APs cost the host almost nothing; the boot CPU waits only for the last parts of its own job, and otherwise idles as before (`WaitForEvent`).
- **The raster in bands.** `PlatformRaster` splits a draw, blit, copy (of memory outside the heap) or fill of at least 32768 pixels into one horizontal band per CPU (at least 8 rows each): every band runs the whole draw with the full clip and the same arithmetic (where a quad's texture coordinates start depends on the clip, not the band) and writes only its rows, so the pixels are those of one CPU, to the bit. `SoftwareRaster bands: n` forces n bands for any size (`SoftwareGPUBandsTest`: SoftwareGPUTest in 3 bands; `RASTER_BANDS=4 tests/raster/run.sh` replays recorded World frames in bands one after the other).
- **Background compilation.** `UefiJitPlatform`'s helper thread is the last AP online (`UefiMp>>startJit:`), its mutex a spin lock and its condition a counter (docs/jit.md, Background compilation); while it waits it takes parts of parallel jobs. The back end it runs uses the optimizer's static arrays, no allocator (`UefiLibC`'s `malloc` is the firmware's pool, the boot CPU's alone).
- **Measured** (arm64 under KVM on the DGX Spark, 4 CPUs against 1, `UEFI_GPU=virtio-gpu-pci` at 1920x1080, the idle World re-rendering every layer each frame, medians after warm-up): a frame 4.0 ms to 2.85 ms, the raster primitives in it 2.1 ms to 1.1 ms (draws 0.93 to 0.37, blits 0.45 to 0.27, copies 0.52 to 0.29, fills 0.19 to 0.16: memory bandwidth), the rest Smalltalk and the firmware's `Blt`. Richards' first iteration (compiling) 5.3 ms to 2.6 ms, its first five 12.0 to 7.2 ms.
- **Bare metal** (a DGX Spark, any Arm SBBR machine): its firmware runs at EL2 and has the ACPI MADT and FADT; PSCI by SMC at EL2 is what `make uefi-run QEMU_UEFI_MACHINE="qemu-system-aarch64 -machine virt,virtualization=on -cpu max -device ramfb"` runs. If the firmware has MP services, they are used instead.

## Pinning

On a machine with two kinds of core QEMU should run on the fast ones. The DGX Spark has ten Cortex-X925 (3.9 GHz: CPUs 5-9 and 15-19) and ten Cortex-A725 (2.8 GHz, about half as fast for the VM); Linux places a thread by how busy it has been, so the vCPU of an idle World wakes on an A725 for each burst of work (a frame, a key, an evaluation) and only a long computation moves it to an X925.

`UEFI_AFFINITY` says where QEMU runs (`tools/qemu-pin.sh`): `big`, the cores of the highest `cpuinfo_max_freq` (Linux, where there is more than one kind; elsewhere unpinned), a `taskset` list such as `5-9,15-19`, or empty or `none`, anywhere. Pinned, QEMU runs under `taskset -c` with its threads named (`-name samaltak,debug-threads=on`), `-smp` is cut to the cores of the list, and each vCPU thread (`CPU n/KVM`) is pinned to a core of its own, the least busy of the list as QEMU starts; the other threads (the main loop, which does virtio-gpu's transfers, I/O) stay on the list. Its log line says where: `qemu-pin: QEMU on CPUs 5,6,7,8,9,15,16,17,18,19; vCPU 0 on 6, vCPU 1 on 7, ...`. The World (`uefi-ui`, `uefi-control`, so `samaltak-ctl open --uefi`, which also takes `--affinity` and `--cpus`) runs on `big` unless `UEFI_AFFINITY` is set; `uefi-run`, `uefi-boot` and the tests stay unpinned, as gates run at once and would crowd onto the same few cores. `samaltak.vncWorld` opens the operator's World with `big` and 4 vCPUs.

Measured (the World at 1920x1080 on `virtio-gpu-pci`, 4 vCPUs, the machine shared with other agents, load about 2): 25 times fib(25) after 150 ms idle, as a click or a key does, 0.90 ms pinned against 0.93 to 1.5 ms unpinned (the median of a run: an A725); a re-rendered frame 3.5 to 3.7 ms pinned, 3.3 to 5.2 ms unpinned; on the A725s alone (`UEFI_AFFINITY=0-3`) fib(32) under the JIT 44 to 51 ms against 27, and a frame 5 ms. A long computation unpinned soon runs on an X925 (fib(32) 27 to 29 ms either way).

## Limits

- Files are read-only and only ext2/3/4 volumes' (docs/files.md); no processes or ptys; no shaders but the Renderer's. TLS is the Smalltalk client's: TLS 1.3 and 1.2 (docs/tls.md).
- The network: one NIC (the first the image has a driver for, else the firmware's first Ethernet one), IPv4 only, no IP fragments, multicast or IP options sent; TCP without window scaling, SACK, timestamps or keepalives.
- Software rendering: a typical 1280×800 frame takes about 4 ms natively, 100 ms or more under QEMU without KVM.
- Memory is physical: the heap's reservations (twice `--max-heap` plus the young space) are allocated and zeroed at start. `make uefi-run`, `uefi-boot` and `test-uefi` pass `--max-heap 256` and give QEMU 2 GB; the World (`uefi-ui`, `uefi-control`, so `samaltak-ctl open --uefi`) gets `--max-heap 1024` in 4 GB (`UEFI_WORLD_HEAP_MB`, a quarter of `UEFI_WORLD_RAM_MB`). `UEFI_HEAP_MB` and `UEFI_RAM_MB` override both. A quarter, because the heap takes twice its limit and the rest of the RAM is for the firmware, the VM and what the image keeps outside the heap: the SoftwareGPU's textures (a Form shown at 1920x1080 is 8 MB there too), the back buffer and the drivers' buffers. Measured at 1920x1080 on arm64: the idle World uses 57 MB of heap; each screenshot an agent shows was 8.4 MB more until the conversation kept only its newest four (docs/agent.md, Images). With 1 GB in 4 GB 1.7 GB stay free outside the heap; 768 MB in 2 GB left 144 MB. Near the limit the VM signals `OutOfMemory` or `StackOverflow` rather than dying (docs/implementation.md, Primitive interface); `LowSpaceTest` boots in a 128 MB heap in `test-uefi`.
- The firmware's timer resolution, its block device drivers. APs run only the raster's bands and the JIT's back end; on x86-64 without MONITOR/MWAIT (KVM does not offer it) an idle AP pauses in a loop.

## Real hardware

`make usb-image` makes `$(OUT)/uefi-$(UEFI_ARCH)/usb.img` (`USB_IMAGE`), one file that is the whole boot disk, for `UEFI_ARCH` `arm64` (this machine's on the DGX Spark) or `x86_64`: a GPT with 1 the EFI system partition (FAT32, 64 MB: `EFI/BOOT/BOOTAA64.EFI` or `BOOTX64.EFI` and `samaltak.args`), 2 the image store (`samaltak-image`: 1 MB and two slots of three times the image, about 350 MB; `UEFI_DISK_MB`'s 512 do not apply), 3 an ext4 volume labelled `usb-files` (`USB_FILES`, a directory: test-uefi's fixture by default, `USB_FILES=` for none), mounted at `/` and `/mnt/usb-files` (`FirmwareBlockDevice all` hides the store and its disk, not the store's sibling partitions). It needs no root: `sgdisk` on the file, mtools (`mformat`, `mmd`, `mcopy`; Debian's `mtools`) for the FAT32, `mkfs.ext4 -d`, `dd` into the offsets. `samaltak.args` is `--max-heap USB_HEAP_MB disk:` (2048) and `USB_ARGS`: the World in the firmware's mode, or `USB_SCREEN=1920x1080`'s. `make usb-run` boots the file in QEMU (`USB_DEVICE=usb-storage` or `nvme`; `UEFI_VNC=N` for its screen) before it goes on a stick; `make test-usb-image` builds one and boots that very file as a USB stick and as NVMe: the diagnostics must find the store, the ext4 volume, a DHCP lease and write their file to the ESP, then a snapshot is written to the stick's store and resumed. The same stick works on a PC (x86-64 build) or another arm64 UEFI machine with Secure Boot off. The pointer needs the firmware's USB mouse driver (most PC firmware has one; OVMF does not). The network needs an Intel 82574L or a virtio-net, else a NIC the firmware (or its option ROM) has a driver for: the VM's `UefiSnp` drives the firmware's first simple network protocol.

**Diagnostics.** `make usb-image USB_DIAG=1` boots into `FirmwareDiagnostics runThenWorld` (System-Storage): one line per finding, each starting `diag `, on the console and in `samaltak-diag.txt` on the stick's EFI system partition (written after each section, so a hang leaves everything before it), then the World after a key or 30 s. `USB_DIAG=key` powers off after a key instead, `USB_DIAG=quit` at once. What it reports, in this order (the risky last): the firmware's vendor, revision and UEFI version, the VM's banner, the configuration tables; SMBIOS (BIOS, system, board, each processor's cores and threads, the memory devices' total); ACPI (the tables, PSCI and its conduit from the FADT's ARM_BOOT_ARCH, the MADT's CPUs (enabled, MPIDRs, GIC version), the SPCR's serial console); MP services' processor count (the VM runs on the boot CPU only); the memory map (free, loader, boot services, runtime, ACPI, reserved, MMIO in MB; the free descriptors' attribute capabilities); memory protection (`EFI_MEMORY_ATTRIBUTE_PROTOCOL` and a pool page's attributes, the CPU architectural protocol, the memory attributes table); the timer's period and what a 1 ms `Delay` takes; `EFI_RNG_PROTOCOL` (its algorithms, a GetRNG); each graphics output (its device path, current mode, every mode with its size and pixel format (`RGBX`, `BGRX`, `BitMask`, `BltOnly`), framebuffer or none, the monitor's EDID: manufacturer and preferred mode); the PCI functions (vendor:device, class, whether a firmware driver has them); every block device and partition (size, GPT name and type, removable, read-only, which is the image store); the volumes mounted and why one did not; each simple network protocol (device path, state, MAC, link, UNDI); and last `NetworkStack active` with a DHCP attempt of 20 s. A section that fails says why, and the next runs. With a serial port the console goes there (docs above), so the lines are also written to the firmware's text console (under QEMU, both are the serial port: each line shows twice).

### First boot on the DGX Spark

The DGX Spark (GB10: 10 Cortex-X925 and 10 Cortex-A725 cores, a Blackwell GPU, 128 GB of memory shared by both, NVMe, Realtek 10GbE and ConnectX-7) has AMI's arm64 UEFI firmware. The VM is arm64 already; what is unknown is the firmware. A checklist:

1. **Build** on any Linux with the tools above (the Spark itself is arm64): `make usb-image USB_DIAG=1` (and keep a plain `make usb-image` for later). Try it first: `make usb-run`, or `make test-usb-image`.
2. **Write the stick** (it erases it): on Linux `lsblk` to find it, then `sudo dd if=build/uefi-arm64/usb.img of=/dev/sdX bs=4M conv=fsync status=progress`; on macOS `diskutil list`, `diskutil unmountDisk /dev/diskN`, `sudo dd if=build/uefi-arm64/usb.img of=/dev/rdiskN bs=4m`. The GPT's backup header ends where the file does, not at the end of the stick: firmware reads the primary one; `sudo sgdisk -e /dev/sdX` moves it if a tool complains.
3. **Firmware setup.** Secure Boot must be off (the EFI application is unsigned): enter setup (on AMI's firmware usually Del or F2 at the logo; the logo screen names the keys), Security, Secure Boot disabled. Leave the boot order alone: DGX OS stays the default.
4. **Boot it once** from the one-time boot menu (on AMI usually F11, else F7 or Esc; or setup's Save & Exit, Boot Override): pick `UEFI: <the stick>, Partition 1`. A USB 3 port on the back; a monitor on the HDMI port before power-on (the firmware's graphics output is found at boot).
5. **Read the console.** The diagnostics print their lines on the screen (and wait 30 s, or a key, before the World): photograph them. What to look at first: `gop` (a mode at all; BltOnly or a framebuffer; is the monitor's EDID preferred mode among the modes: `USB_SCREEN=WxH` picks one), `block ... the image store` (else the VM could not have loaded: see below), `volumes`, `snp` (is the Realtek there, link up, UNDI) and `dhcp` (an address in 20 s), `rng` (none: no TLS), `mp services` and `madt cpus` (20 expected), `memory attribute protocol` and `cpu architectural protocol`.
6. **Get the file back.** `samaltak-diag.txt` is in the root of the stick's FAT32 partition: plug the stick into a Mac or PC (it mounts as `SAMALTAK`), or on Linux `mcopy -i /dev/sdX@@1M ::/samaltak-diag.txt .` (no mount, no root if the device is readable), or from the file: `mcopy -i usb.img@@1M ...` after `dd` back. Each boot replaces it; it ends with `diag done` unless something hung, and the last line says where.
7. **Then the World**: after the key, or boot the plain stick. To drive it from another machine, `make usb-image USB_CONTROL=1` and `samaltak-ctl connect` with the token it shows at boot (docs/remote.md: the token, the network, an SSH tunnel). With 128 GB, `USB_HEAP_MB` can be far larger than 2048 (the heap takes twice its limit, allocated and zeroed at start: docs above, Memory).

Known risks, and what each looks like:

- **Memory attributes on AMI's arm64 firmware.** edk2 maps a loaded image's code read-only and its data non-executable; the VM's one section is both, so `efi_main` first makes itself writable and executable with `EFI_MEMORY_ATTRIBUTE_PROTOCOL`, else the CPU architectural protocol's `SetMemoryAttributes` (docs above). If AMI's firmware protects images otherwise (or neither protocol is there, or the call is refused), the VM faults at its first write to a global, before any output: the firmware prints a synchronous exception (ESR, ELR) or hangs right after the boot menu, with nothing from samaltak and no `samaltak-diag.txt`. Report the exception's text; the diagnostics cannot help, as they run in the VM.
- **Graphics modes.** The firmware's GOP comes from NVIDIA's display driver, with the modes it offers for the monitor it found at boot (some firmware offers only the monitor's native mode, or only 1024x768, or none without a monitor at power-on). The World opens in the mode it booted in unless `--window-size` names another one; a mode without a framebuffer (`BltOnly`) works through `Blt`, more slowly. A 4K mode is 33 MB a frame in software: slow; prefer `USB_SCREEN=1920x1080` if listed. No `gop` line: no screen at all; the World cannot open (boot the plain stick with `USB_ARGS=--headless` and the control service instead).
- **Network: Realtek via SNP.** The image has drivers for the Intel 82574L and virtio-net only; on the Spark the VM's `UefiSnp` drives the firmware's first simple network protocol, which is whatever AMI's firmware (Realtek's UNDI driver, or a ConnectX-7 option ROM) installed first, if it installs one at all (network stacks are often off in setup: enable the network stack / PXE support for the onboard NIC). The `snp` lines show which NICs have one and in what order; `dhcp: no lease` with an `snp` line that is link down means another port or another cable.
- **The console.** Output goes to a serial port when the firmware has one (`spcr` names it), else to the screen; the diagnostics write to both, but the VM's own messages (a fatal error, `samaltak: exit N`) go only to the serial port then.
- **Timer and CPUs.** The firmware's timer period bounds the scheduler's resolution (`timer period`, `a 1 ms Delay takes`); the VM runs on the CPU the firmware booted on, which may be an A725 (about half as fast as an X925). The others it starts itself (docs above, More than one CPU): with the firmware's MP services if AMI's firmware has them, else PSCI by SMC at EL2 from the ACPI MADT and FADT; the console's first line from the VM says which and how many (`samaltak: 20 CPUs (PSCI by SMC at EL2)`). `samaltak: 1 CPUs` means neither worked: everything runs on the boot CPU as before.
- **USB.** Some firmware enumerates USB 3 sticks only on certain ports, or not as a boot option until setup's fast boot is off.
