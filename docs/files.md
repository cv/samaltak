# Files on UEFI

On an operating system `File`, `FileStream` and `Directory` (System-Files) are the platform's file primitives (docs/platform.md). On UEFI those fail (`UefiNoIO`): there the image reads the machine's ext4 volumes itself, read-only, through the firmware's block devices (System-Storage; the file system is `Ext4Volume`, docs/storage.md), and the same classes show them as one tree.

    Directory entries: '/mnt'                         "#('fixture' 'fixture-gpt')"
    File readText: '/mnt/fixture/hello.txt'
    FileStream readOnlyFileNamed: '/etc/os-release' do: [:s | s nextLine]
    FirmwareVolumes mounts                            "mount point -> Ext4Volume"
    FirmwareBlockDevice all                           "the disks and partitions, without the image's"

## Layout

Each ext4 volume (ext2 and ext3 too) is at `/mnt/<name>`, in the firmware's order of its devices, and the first one is also `/`: on a machine whose first ext4 partition is its Linux root, `/etc/hostname` is that system's and `/mnt` lists every volume. `<name>` is the volume's label (`mkfs.ext4 -L`), else its GPT partition's name, else `volume<n>` (n counts the volumes from 1); `/` and control characters become `_`, a name already taken gets `-2`, `-3`, .... `/mnt` exists even if the root volume has no such directory, and lists the mount points with what the root volume has there. With no volume, `/` is an empty directory. The working directory (`Directory current`) is `/`, and relative paths are relative to it. Paths are resolved by name first (`.` and `..`; `..` of a mount point is the directory it is in), then by the volume, which follows its symbolic links (an absolute target from its own root, as if chrooted there).

Everything is read-only: opening for writing, `File delete:`, `rename:to:`, `Directory create:` signal `FileError` (`Read-only file system: <path>`); a missing file `FileDoesNotExist`, as on an operating system. The image itself is saved to its own store (`UefiImageStore`, docs/uefi.md), not to a file.

## How

- **The facade.** `File mountTable` is nil on an operating system, so nothing changes there. A `MountTable` maps mount points to volumes; the path-taking methods (`File stat:`, `File open:mode:`, `delete:`, `rename:to:`, `Directory entries:`, `create:`, `current`) ask it first if it covers the path. A file opened on a volume is a `VolumeFile`, which `FileStream` holds where it holds a platform handle: File's handle primitives fail for it and their fallback code sends it the operation (read, size, position, seek; write signals), so FileStream is unchanged, buffering included (8 KB reads). A table covers either every path (UEFI) or only those under its mount points, the rest staying the platform's: on an operating system `File mountTable: (MountTable new mount: (Ext4Volume onFile: 'disk.img') at: '/tmp/disk'; yourself)` puts an image's files under `/tmp/disk` (the File Browser shows them). A volume answers `stat:` (an object with `isDirectory`, `size`, `modificationTime` in UTC µs, and `readFrom:count:`) and `entriesAt:`; `Ext4Volume` does.
- **Mounting.** `FirmwareVolumes` (a start-up class) installs a table that covers everything at each start on UEFI (and drops it when an image saved there starts on an operating system). The table looks for volumes on its first use, not at start: every `FirmwareBlockDevice` whose bytes 1024–2047 have ext4's superblock magic (16rEF53) is an `Ext4Volume`; one that does not mount is left out and its reason kept (`FirmwareVolumes problems`).
- **Block devices.** `FirmwareBlockDevice` is a `BlockDevice` over the firmware's `EFI_BLOCK_IO_PROTOCOL` (UEFI 2.10, 13.9), through `Firmware` and `Machine` (System-Devices): a handle for each disk the firmware's drivers found (NVMe, virtio-blk, USB mass storage, AHCI, SD) and a child handle for each partition of its GPT or MBR (`isLogicalPartition`). A read calls `ReadBlocks` into a buffer outside the heap, of 256 KB of whole blocks, aligned to the medium's `IoAlign`, then copies into the ByteArray; the medium (`blockSize`, `blockCount`, `isReadOnly`, `isRemovable`, `mediaId`) is read at each use. A partition's entry comes from `EFI_PARTITION_INFO_PROTOCOL` (`partitionType` #gpt, #mbr or #other, `partitionName`, `partitionTypeGuid`, `mbrType`), its number from the device path's hard drive node, `description` from `EFI_DEVICE_PATH_TO_TEXT_PROTOCOL` (`PciRoot(0x0)/Pci(0x2,0x0)/NVMe(0x1,...)`). Nothing writes. `FirmwareBlockDevice all` leaves out the disk with the image store, and its partitions: it reads the first block of each device for the store's superblock (`SAMSTORE`), and drops every device whose device path, without its partition node, is that disk's.
- **QEMU.** `UEFI_DISKS` attaches raw disk images read-only, `FILE@DEVICE` with DEVICE `nvme`, `virtio-blk-pci` or `usb-storage`: `make uefi-run UEFI_DISKS="disk.img@nvme"`. `make test-uefi` builds two from `tests/uefi/ext4` (and a `numbers.txt` of 50000 lines) with `mkfs.ext4 -d`: `$(UEFI)/ext4.disk`, a whole disk labeled `fixture`, on NVMe, and `$(UEFI)/ext4-gpt.disk`, unlabeled in a GPT partition named `fixture-gpt`, on virtio; it lists `/` and `/mnt`, reads files, a symbolic link and a file's end through FileStream, checks that writing fails and that the image's disk is not among the devices (`tests/uefi/files.expected`). Needs e2fsprogs and sgdisk (gdisk).

Measured under QEMU with KVM on an arm64 host: finding and mounting both fixture volumes, then listing and reading as above, 20 ms; `File readBytes:` of a 64 MB file 47 ms on NVMe, 73 ms on virtio-blk (a FileStream reads a rest of 8 KB or more straight into its result), the same file in 4 KB `next:` 325 and 262 ms; `FirmwareBlockDevice` reads 8 MB in 5 and 8 ms. USB mass storage (`usb-storage`) works too.
