# Storage

Block devices and a read-only reader of ext2, ext3 and ext4 file systems, in Smalltalk (`System-Storage`, layer 0), so that the image reads Linux file systems where it has no OS: on UEFI through the firmware's block devices, hosted from disk image files.

    volume := Ext4Volume on: (FileBlockDevice on: 'disk.img').    "offset 0 of the device is the file system's start"
    volume entriesAt: '/etc'.                     "names, sorted, without . and .."
    (volume stat: '/etc/passwd') size.            "an Ext4Inode: mode, uid, gid, nlink, size, times, ..."
    volume read: '/var/log/syslog' from: 1000000 count: 65536.
    volume contentsOf: '/etc/hostname'. volume readLink: '/bin'.

## Block devices

`BlockDevice` is the abstract device: `blockSize`, `blockCount`, `isReadOnly`, `read: count blocksAt: lba` (a ByteArray) and `read: count blocksAt: lba into: bytes startingAt: index`, each defined by the other, so a subclass implements one; `readBytes: count at: byteOffset [into:startingAt:]` reads any byte range, the partial blocks at its ends on their own and the whole blocks between in one call. Reading outside the device signals `FileError`. `FileBlockDevice on: path [blockSize: n]` reads a disk image file on the host (512-byte blocks by default) through System-Files' primitives, straight into the caller's buffer; `FirmwareBlockDevice` reads the firmware's Block I/O on UEFI, where `FirmwareVolumes` mounts the volumes for `File` (docs/files.md).

## Ext4Volume

- **Mounting.** `Ext4Volume on: aBlockDevice` reads the superblock at byte 1024: magic, revision 0 or 1, blocks of 1 to 64 KiB, the feature flags. What it cannot read it refuses with a `FileError` that names it: compression, dirdata, an external journal device (journal_dev), unknown incompatible features. Read-only compatible features never stop it (that is what they are for). With metadata_csum the superblock's CRC-32C (`Crc32c`) is verified; no other checksum is. A journal that needs recovery (needs_recovery) or a file system marked with errors mounts with a warning (`warnings`, and a line on the Transcript): the journal is not replayed, so what it holds and the file system does not yet is missing.
- **Groups and inodes.** Group descriptors of 32 bytes, or `s_desc_size` (64) with 64bit; after the superblock, or with meta_bg from `s_first_meta_bg` on in the first group of each meta group, after its backup superblock if it has one (sparse_super: groups 0, 1 and powers of 3, 5 and 7; sparse_super2: the two `s_backup_bgs`). Only the inode table's location is used; it is cached per group. Inodes of 128 bytes to a block, their extra fields where `i_extra_isize` covers them: nanoseconds and the two epoch bits of each time (to 2446), the creation time; uid and gid with their high 16 bits, 64-bit sizes, `i_blocks` in 512-byte units or, with huge_file and the inode's HUGE_FILE flag, in blocks.
- **File data.** An inode's logical blocks map to runs of physical ones (`runsFrom:count:`): through its extent tree (any depth: each index node's last entry at or before the block, a binary search; a leaf's extents, then a hole up to the next leaf's first block), uninitialized extents and holes as zeros; through an ext2/3 block map (12 direct blocks, an indirect, a double and a triple indirect one, a zero pointer a hole for its whole subtree); or from inline data (inline_data: `i_block`'s 60 bytes, then the in-inode extended attribute `system.data`). `readFrom:count:` allocates the result once and reads each contiguous run in one device call straight into it; holes cost nothing. Metadata blocks (extent and indirect blocks, inode tables, directories) go through a cache of the last 4 MB read; data blocks do not.
- **Directories.** Linear directories and htree (dir_index) ones alike are read block by block: an htree's root and index blocks hold only entries of inode 0 (`.` and `..` cover the root's index), which are skipped, so the leaves' entries remain, in their order on disk. Entries with and without file types (filetype), `rec_len` as 64 KiB blocks encode it, inline directories (the parent's inode number, then entries). Name lookups use a table of each recently used directory's names (256 directories): a path resolves without reading a directory twice.
- **Paths.** From the root, absolute or not; `.`, `..` (the directory's own `..` entry), and symbolic links, fast (the target in `i_block`, as the kernel decides: no blocks but its attribute block's) or slow (in a block), followed in the middle of a path always and at its end except for `lstat:` and `readLink:`, at most 40 a lookup (`Too many levels of symbolic links`). A missing name signals `FileDoesNotExist` ('No such file: path', its path), the rest `FileError`: 'Not a directory', 'Is a directory', 'Not a regular file' (devices, FIFOs, sockets), 'Encrypted' (files and directories with ext4 encryption are refused one by one), 'Corrupt ext4 file system' with what is wrong. In a casefolded directory a name that is not there exactly is compared lowercased (not the kernel's Unicode folding).
- **Interface.** `stat:`/`lstat:` answer an `Ext4Inode` (`fileType`, `isDirectory`, `isSymlink`, `permissions`, `size`, `uid`, `gid`, `nlink`, `blocks`, `atime`/`mtime`/`ctime`/`crtime` in seconds with `...Nanoseconds`, `modificationTime` in UTC microseconds as `File modificationTime:`), which also reads by itself (`readFrom:count:`, `contents`, `linkTarget`, `directoryEntries`), so a reader resolves a path once. `entriesAt:` answers sorted names, `directoryEntriesAt:` `Ext4DirectoryEntry` objects (name, inodeNumber, fileType) in their order on disk; `label`, `uuid`, `features` (mke2fs's names), `blockSize`, `blockCount`.

## Tests

`Ext4VolumeTest` (Tests-Storage) runs `tests/storage/ext4_fixtures.sh`, which makes a tree of files and ten images of it with e2fsprogs (`mke2fs -d`, no root needed) into `ext4-fixtures` beside the image, again only when the script changes (about 4 s); without e2fsprogs every test fails saying so. The tree: nested and empty directories, files at every block boundary up to 1 MB, 16 MB of random bytes, a sparse file with a trailing hole, a 5 GiB sparse file with data across 4 GiB, a file of 400 one-block islands (an extent tree of depth 1 on 4 KiB blocks, 2 on 1 KiB), symbolic links of both kinds (relative, absolute, to a directory, dangling, loops), hard links, Unicode names, a FIFO, a setuid file, a sticky directory, a directory of 2000 entries with names of up to 255 bytes. The variants: ext4 with 1, 4 and 64 KiB blocks, without 64bit (gdt_csum), with 128-byte inodes, with inline data, with meta_bg and sparse_super2 (96 groups); ext3 and ext2 (block maps) with 4 and 1 KiB blocks, ext2 without file types on 2 KiB blocks. After mke2fs, debugfs sets nanosecond and post-2106 times, a uid and gid above 65535 and uninitialized extents (whose blocks are then filled with 0xFF, which must still read as zeros), and `e2fsck -fD` indexes the big directories. Every variant is compared with what the host sees (find's manifest and the files): every file's type, permissions, owner, link count, size, modification time, bytes (small files whole, up to 32 MB in pieces at odd offsets, the 5 GiB file around its data), link target, every directory's names. More tests read at offsets across block and extent boundaries, resolve odd paths, and patch images (`PatchedBlockDevice`) into unsupported features, a wrong superblock checksum, a journal that needs recovery, an encrypted file, a broken extent header.

**Measured** hosted (this machine's page cache, arm64, the default JIT): reading the 16 MB file in one call 1.3–3.7 GB/s, in 64 KiB reads 2.4–4.4 GB/s with extents and 0.7 GB/s with ext2's block map on 1 KiB blocks; listing the 2000-entry directory 0.8–6.5 ms the first time (one read of the directory) and 0.7–1.2 ms after; looking up all 2000 names 5–20 ms.
