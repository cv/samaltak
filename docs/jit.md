# JIT

Two compilers on a shared runtime: `baseline` (Cog-style) and the optimizing tier `opt`, whose lower tier is baseline code. Both are written in Smalltalk: Lowtalk for code in the VM (translated to C like the rest of it), ordinary Smalltalk for code in the image. No LLVM at run time. Target: Apple Silicon (M2 Max, arm64, macOS). Both beat Pharo 12's Cog JIT on every Are We Fast Yet benchmark (Comparison, docs/benchmarks.md).

| `--jit` | what |
|---|---|
| `none` | the interpreter (computed goto, PGO) |
| (all) | married Contexts: closure creation does not flush frames (in the interpreter, for every mode) |
| `baseline` | Cog-style: own arm64 assembler, simulated operand stack in registers, machine-code inline caches (monomorphic, polymorphic, megamorphic), inline SmallInteger/Float arithmetic and common primitives |
| `opt` (default) | baseline code plus an optimizing tier in the VM (Lowtalk): SSA IR, inlining from type feedback, closures not made, unboxed Floats, linear-scan register allocation, deoptimization to frames |

Each compiler has ablation flags (`--jit-flags -ic,-arith,...`) so that the effect of each optimization is measured separately.

## Shared runtime

The interpreter's frames are the canonical state. Machine code runs on the same frame records and C-stack slots; at every safepoint (a call out of machine code that may allocate, collect, flush frames, switch processes or run Smalltalk) the values it holds in registers are in their slots and the frame's `pc`/`sp` are valid. Hence:

- the interpreter can resume any frame of compiled code at its bytecode pc, and compiled code can be entered at the pc of a frame the interpreter was running (on-stack replacement at backward jumps, return into a compiled caller);
- GC roots, `materialize_all` (frames into Contexts), the debugger, stack printing and process switches stay as they are;
- deoptimizing baseline code is free; flushing the code cache only needs no machine code on the native stack.

**Frames.** A `Frame` has a `code` field: its method's `JitMethod` (machine code), 0 (none), or 1 to 0xFFFF while the JIT counts it (activations, then backward jumps). Every frame push sets it: from the method cache entry (`K_JIT` entries hold the code or 1; `fillCache` asks `JitRuntime`), for blocks from the home method's code. Machine code keeps `pc` and `sp` (one 64-bit store) current at safepoints instead of `ip`; the runtime turns them into `ip`, `nframes` and `cstackUsed` (`Interpreter>>syncFrame:`). Operands live in their slots at offsets known at compile time (`BytecodeAnalysis`: the depth before every instruction).

**Native stack.** Machine code calls compiled callees with `blr` and returns with `ret`, so the native stack mirrors the frames entered since the last `jit_enter`, 16 bytes (x29, x30) per activation. `jit_enter(frame, address)` (`JitStubs`, generated at startup) saves the callee-saved registers, sets x19–x22, remembers the native stack pointer, pushes x29/x30 as a prologue would and branches to `address`. Leaving to the interpreter resets the native stack to `jit_enter`'s and returns: `exitSync` (the code stored the frame's pc and sp: the interpreter continues there), `exitPlain` (the runtime made the frames canonical). Returning from the first activation lands in the trampoline, which answers the caller's frame; the runtime continues its machine code if it has some (`JitRuntime>>run:at:`), else the interpreter.

**Registers** (callee-saved, pinned): x19 the frame record, x20 its slots (`fp`, receiver at `fp[-1]`), x21 the receiver, x22 the `JitState` (nil/true/false and the classes inline paths check, refreshed after every GC; the interrupt flag; the frames array; jit_enter's stack pointer; the young space's bounds). x23–x25 hold nil, true and false, x26–x28 are free for register allocation (opt); x0–x17 scratch. Code entered by a caller that pushed its frame (the runtime's sends, optimized code calling baseline code) starts with the prologue (`JIT_PROLOGUE_BYTES`: x19 := the next Frame, push x29/x30, load x20, x21); its start is after the prologue.

**Calls into the runtime.** Machine code stores pc and sp, calls a stub (`ldr x16, =function; br x16`, in the code cache so that `bl` reaches it) with the frame in x0; after a safepoint it reloads x21. The runtime answers 0 (continue), 1 (leave: `exitPlain`) or, for a send, the callee's entry (frame pushed; the caller `blr`s it). If frames were flushed (process switch, `thisContext`, stack full), or code was invalidated, it answers 1. Sends through the runtime (`OptRuntime>>send:index:site:` for optimized code's calls that no machine code takes, `JitRuntime>>dispatch:frame:argc:`) use the interpreter's inline caches, keyed by the site's code address: frameless sends (^ivar, constants, setters) touch the frame only when an interrupt is pending (they are safepoints, as in the interpreter); leaf primitives and primitives run as in the interpreter; a method with code gets its frame pushed from the cache entry; a method without code is counted (compiled at the threshold) or its frame is pushed and the interpreter runs it; `perform:` sends its selector, the arguments moved down over it as the primitive does, and a selector not understood sends `doesNotUnderstand:` with a Message of it and the arguments, as the interpreter does; a send the runtime cannot complete cleanly (a married receiver, a full stack; a `perform:` whose primitive fails, of a selector not understood or of `perform:`) leaves to the interpreter to execute it again, which it can because nothing happened yet. Special selectors first try the interpreter's fast paths, `value`/`value:` on blocks enter the block's code. Closures and Arrays (`0x94`) are runtime calls.

**Interpreter hooks.** Activating a method whose cache entry is `K_JIT` (count, compile, enter at start: `JitRuntime>>activated:`), returning or non-locally returning into a frame with code and activating a block whose home has code (continue at `ip`: `resume:`), a backward jump in a frame whose `code` is not 0 (count, compile, on-stack replacement: `backJump:`). Process switches flush all frames, often (the sampler), so returning into or jumping back in a Context whose method has code marries the Context to a new bottom frame, its sender the base, and continues it in machine code (`resumeContext:`, `Interpreter>>thawFor:`); otherwise long-running loops would stay interpreted and every return into them would leave machine code. With `--jit none` they cost a load and a branch on paths that already do work. The bytecode-pc to machine-pc map holds the resumption points: method and block starts, continuations after sends, loop heads, conditional jumps (a `mustBeBoolean` send returns to them).

**Exits.** A compiler may leave to the interpreter at any instruction (`exitSync`): baseline code does for `thisContext`, non-local returns, `mustBeBoolean`, stores into immutable objects and returns from the bottom frame. The interpreter continues the frame and comes back at the next send, return or backward jump.

**Code.** One `MAP_JIT` region (`pthread_jit_write_protect_np`, `sys_icache_invalidate`), bump allocated after the stubs; it takes the place of a zero-fill array in the VM's image (`CodeCache`), near the VM's data, so that `adrp` from the code reaches it (tiering counters, type feedback, eden's top, call caches). A compiled method's header (`JitMethod`) follows its code: the method (a GC root), the compiler, start, the bytecode map, the notes. Methods are found by identity hash (stable across moves) in a 64K open-addressed table; activations are counted per hash. Scavenges update the methods of headers compiled while the method was young (a list); full GCs and become all of them. Literals are in the code: baseline code's literal pool, optimized code's oop pool (GC roots). When the cache (or the table) is full the method stays interpreted and the whole cache is flushed at the next interpreter hook, when no machine code is on the native stack: frames go back to counting, the method caches are flushed. Become of a compiled method kills its code (its frames are interpreted from then on). Method dictionary changes flush the interpreter's caches, which the runtime's sends use. Snapshots flush the frames; machine code is not saved.

**Triggering.** `--jit-threshold N`: activations before a method is compiled (0: the first); `--jit-osr N`: backward jumps in an interpreted frame before its method is compiled and the frame continues in machine code. `--jit-cache MB` (1–128).

**Disassembly.** The machine code of any method can be shown from the image, for either compiler (compiling it if needed, `CompiledMethod>>machineCode`, `machineCodeFor: #baseline`, the System Browser's method menu): every instruction, grouped under the bytecode it implements (with the source line), and commented with what it does (tag check, overflow branch, spill, call into the runtime by name...). Compilers record the comments as they emit (always for a disassembly, for all code with `--jit-flags notes`; a copy compiled for a disassembly is dropped and leaves the feedback alone); `jitCode` answers code, address, bytecode map, notes and stub names; `Arm64Disassembler` prints them.

**Statistics** (`vmStats`, `VMStatistics`): methods and bytecodes compiled, microseconds compiling, code bytes, cache flushes, entries into machine code, exits, resumptions, on-stack replacements, methods that could not be compiled.

**Constants.** The code generators (`JitStubs`, the compilers) are `Arm64Module`s, so they name registers and conditions; the runtime and the analysis are `VMCoreModule`s, with the VM's helpers and constants. Neither needs the other's class variables: the generators ask the runtime through inline accessors (`runtime arith`, `runtime prologueBytes`), struct offsets come from the structs (`(self cCoerce: 0 to: 'Frame *') fieldAddress: #fp`).

## Compilers

`JitRuntime>>compile:mode:notes:` analyzes the method (`BytecodeAnalysis>>analyze:`), then has the mode's compiler emit at the assembler's pc; it appends the header, installs it and counts. A new compiler:

- a module subclassing `JitCompiler` (its conventions: prologue, `emitSync:depth:`, stubs, frame and state offsets) with `compile: aMethod` answering whether it emitted every reachable instruction; it records resumption points (`runtime noteResume:at:`);
- its mode in `JitRuntime>>modeNamed:` / `modeName:` and a case in `compile:mode:notes:`; its flags in `flagNamed:length:` (queried as inline accessors);
- if it keeps values in registers, spills before every runtime call and at every resumption point.

**Baseline** (`JitBaselineCompiler`, `JitBaselineRuntime`, `--jit baseline`). After Cog's StackToRegisterMappingCogit: one pass over the bytecodes with a simulated operand stack whose entries are in their slot, in a register (x0–x8, x12–x15), a constant, nil/true/false (pinned in x23–x25), self (x21), a temp or a literal not loaded yet, or an unboxed Float (d8–d15). Values go from producer to consumer in registers, constants become immediates, folded where both are known; the stack goes to its slots at sends, runtime calls and merge points (which start with every entry in its slot). Before an instruction that may send, everything below its operands is written back (unboxed Floats stay: its slow path boxes and reloads them around the send), so its slow path stores only the operands. Layout: checked entry, unchecked entry, frame code, the bytecodes in pc order (block bodies with their entries), slow paths, resumption stubs, the literal pool, the `JitMethod` header (`adr` reaches it).

- *Sends*: the receiver in x0, receiver and arguments in their slots, `add x20` to the callee's fp, `ldr x9` the site's class from the pool, `bl` the site's target, `sub x20` after; the result comes back in x0. The target is the miss stub while unlinked; a compiled method's checked entry when monomorphic (its class check against x9: tag test, class word, compare; immediates by tag out of line); a `BaselinePic` of up to 6 classes, each branching to its target's unchecked entry; or, megamorphic, the megamorphic stub (x9 then holds the selector; a 4096-entry table probed in machine code). The miss stub calls `JitBaselineRuntime>>miss:receiver:ret:`, which looks the send up (the interpreter's global cache), compiles the target at the threshold, links or relinks the site (code patched under the W^X toggle) and jumps to the target; it leaves to the interpreter for `doesNotUnderstand:`, married Contexts, `perform:` and uncompiled targets. Young classes are cached too (their words become young roots). Method dictionary changes (`flushMethodCache`, `flushCacheFor:`), become and dead code unlink every (or every such) site. Super sends link once to the unchecked entry. Each site's state is its type feedback: `JitBaselineRuntime>>feedbackSitesOf:` and friends (pc, selector, state, receiver class and target per case), `CompiledMethod>>jitSendSites` in the image.
- *Frames*: the callee compares its fp against the JitState's stack limit (0 while an interrupt is pending: the one compare is also the interrupt check), pushes the native record (x29, x30) and its Frame with two `stp`s and a `str` (code, closure and ctx nil, fp, pc and sp 0), x21 := the receiver, nil into its temps; a return pops both after one check (a married frame, or frame 0, which `run:at:` marries, takes the slow path). A Frame's method, pc, sp, ip and lits are lazy: the runtime makes a suspended frame canonical from the return address in its callee's native record (`canonicalizeBelow:`, the method's return map: return offset, pc, depth, argc, length, pushes; frame f's record is at `baseRecord − 16·(f − baseFrame)`), top down, stopping at the first frame that already is (a zero pc marks a frame pushed since). Every runtime entry that may collect, flush or leave does that first (`JitRuntime>>sync:`, the exit stub).
- *Quick methods* (^ivar, ^self, ^constant, ^literal, setters) run without a frame; with an interrupt pending they take the frame's path (sends are safepoints). *Primitives* run before the frame: in machine code for `basicNew`, `basicNew:` (eden bump allocation with the identity hash generator inline), `==`, `class`, closure `value`, SmallInteger and Float arithmetic and comparisons, SmallInteger `quo: rem: // \\`, `sqrt`, `truncated`, `charValue`, `Character value:`, `identityHash`, `at: at:put: basicSize` (pointers without fixed fields, 32-bit words, bytes), `uint32At:` and `uint32At:put:` of bytes; the others through their C function (`prim:fp:fn:info:`; leaf ones without canonicalizing). Failure continues into the frame and the body.
- *Inline at send sites*: SmallInteger `+ - * // \\ bitAnd: bitOr: bitShift:` and comparisons (tag checks only for operands not known, immediates, overflow branches), compare and branch fused with the conditional jump, jumps threaded into a conditional jump on the value just pushed (`and:`, `or:`). Floats: an operation with an operand that surely is a Float (an unboxed value, a Float constant, a temp whose unboxed value is known in the basic block) decodes the other (SmallFloat64, BoxedFloat64, SmallInteger) and leaves its result unboxed in a d register for the next one; other operations try SmallIntegers first, Floats out of line; boxing (a SmallFloat64, else a BoxedFloat64 from the runtime) happens when a value goes to memory or a send. `== ~~ class` never send, nor do `isNil notNil` while only UndefinedObject and ProtoObject define them (a heap scan; another definition drops all code); `at: at:put:` inline for Arrays, out of line for Strings, Symbols and ByteArrays (`size` is sent: classes define their own, and Arrays answer it from the primitive in machine code); `value value: value:value:` check the closure's class and argument count and call the block stub, which finds the block's entry in a (home method, startpc) cache. Closures and Arrays (`0x94`) are runtime calls; outer temps inline; the store barrier's fast path inline (the remember stub saves the registers).
- *Non-local returns* leave to the interpreter.
- Resumption points: method and block starts (an interrupt check out of line), loop heads, send continuations (a stub loads the result from its slot) unless unboxed values are live there. Exits go through the runtime so that the frames below become canonical.
- Flags (each switches one optimization off, for the ablations): `ic` (inline caches: every send looks up in the runtime), `pic`, `mega`, `regs` (every push to its slot), `arith`, `fuse` (compare and branch, jump threading), `float`, `access`, `prims`, `blocks`, `quick`, `barrier`, and `notes`.

## Optimizing tier

`--jit opt` (`OptBuilder`, `OptPasses`, `OptRegalloc`, `OptCodegen`, `OptRuntime`, `JitFeedback`; Lowtalk in `VM-Jit`). Baseline code is the lower tier; hot methods, blocks and loops are compiled again from their bytecodes with type feedback, inlining and speculation, and deoptimize to frames when a speculation fails.

**Tiering.** In this mode baseline code counts, per method (identity hash), method and block entries and backward jumps (`emitTierUp:depth:loop:`, a decrement of a word in the VM's data). At zero it stores pc and sp and calls the tier-up stub (x0 the frame, x1 whether at a backward jump); `OptRuntime>>tierUp:loop:` answers where the frame continues: the method's optimized code at its start, a block's unit, or a loop's unit (on-stack replacement at the loop head). Units are compiled once per method, per block (method, startpc) and per loop (method, block, loop head); a failed compilation is remembered. Methods whose hashes meet share a count: it starts over at every tier-up, whatever the outcome. A method's optimized code is installed in the method caches and over its baseline code's unchecked entry: a `b` to an entry that builds the frame as baseline code builds it (`JitBaselineRuntime>>redirect:to:`, undone on invalidation; not for quick methods and primitives); a block's unit is what the block stub enters from then on (its cache is cleared). `--jit-opt N` sets the count (default 1000), `--jit-flags eager` makes it 1. Frames resumed after a process switch (Contexts married to new frames) enter loop units too; if their code makes closures, the temps the closures reach stay in the frame (a closure may change them through the Context).

**Calls between the tiers.** Optimized code calls as baseline code does: receiver and arguments in their slots, the receiver in x0, x20 the callee's fp, `bl`, the result back in x0. A method it knows (the receiver's class known or guarded) it calls at its baseline code's unchecked entry (a primitive's machine code first; optimized code through the redirection), a closure it did not make through the block stub (after its argument count), anything else through an inline cache of its own, which `JitBaselineRuntime>>miss:receiver:ret:` links as baseline code's (monomorphic, polymorphic, megamorphic; unlinked with them). What baseline code leaves to the interpreter for (`doesNotUnderstand:`, `perform:`, a married Context, a method not compiled yet) the miss handler sends through the runtime (`OptRuntime>>sendFrom:ret:`), as the entry and block stubs' slow paths do for an optimized caller; the stubs continue where it answers (the callee's entry, its frame pushed, or a `ret`: the result is in the receiver's slot). Callees build their frames (optimized code's entry from such calls builds it as baseline code does), so an optimized frame suspended in a call is lazy too: its return map (return offset, safepoint, argument count) gives `canonicalizeBelow:` and `setTop:ret:mode:` its pc (bytecode size plus the safepoint) and sp. Optimized code answers in x0 and keeps x23–x25 (baseline code's nil, true, false; reloaded after runtime calls). A C primitive that commits its result without switching processes returns into optimized code (the interpreter cannot continue its frame).

**Type feedback** (`JitFeedback`): per (method, bytecode pc) up to 4 receiver classes with counts, `FB_MEGA` beyond, and profile bits: Float operand, non-number operand, overflow, and why optimized code deoptimized there (class guard, arithmetic guard, bounds check, other). It does not depend on the compiler that collects it: baseline code reports every receiver class its inline caches miss on (`noteSend:pc:class:`) and, without a call, sets a byte per site when an inline Float path runs (`floatBitAddressFor:pc:`); deoptimization reports what failed (an arithmetic guard looks at the operands). What baseline code takes inline without a send gives no feedback; the optimizer reads that as the inline case: `at: at:put: size` as Arrays, `value value: value:value:` as BlockClosures (both guarded), arithmetic as SmallIntegers; `isNil notNil` are comparisons with nil while no class but UndefinedObject and ProtoObject defines them.

**IR** (`OptIR`): nodes in fixed arrays (operation, representation oop or double, type: SmallInteger with a range, Float, Boolean, nil, Character, a class), blocks with predecessor edges, frame states (per activation: method, closure, receiver, pc, slot values, chained to the caller's) for every guard and safepoint, inlined activations. `OptBuilder` builds SSA directly from the bytecodes (Braun et al., Simple and Efficient Construction of Static Single Assignment Form, CC 2013), one variable per frame slot of every activation; arguments are never phis, nor are temps that neither a loop nor a closure of their activation (which may be inlined into the loop) stores.

**Inlining.** A send is inlined for the class the receiver is known to have, or speculated from feedback: one class behind a guard, up to four behind a type switch (anything else deoptimizes; at an arithmetic site that saw Floats, which baseline code's inline paths report no class for, it is sent); a mega site, one that deoptimized for a class, and sends without feedback are inline caches; a method with baseline code that is not inlined is called at its unchecked entry (Calls between the tiers). Methods up to 200 bytecodes, 3000 in all, 8 deep, a recursive one once. Blocks evaluated by an inlined `value…` send are inlined into the activation that made them; their closures are never made: frame states describe them (sunk), deoptimization makes them, marrying the frames they refer to. A closure that escapes (stored, passed, answered) makes the compilation start over without inlining the method that made it. A loop's unit (on-stack replacement) inlines the closures its frame made before the loop, in the temps that hold them: guarded by class, startpc and outerContext (the frame's Context), else deoptimize. `^` in an inlined block is a jump to the home activation's return; in a block's unit it deoptimizes, and the unit is not optimized again.

**Primitives and speculation.** SmallInteger `+ - * < > <= >= = ~= // \\ quo: rem: bitAnd: bitOr: bitXor: bitShift:` with tag guards and overflow checks (Boolean results branch directly, no frame state); Float `+ - * / < > <= >= = ~= sqrt` on doubles (SmallFloat64, BoxedFloat64 or SmallInteger operands decoded, the result encoded; out of SmallFloat64's range, a zero divisor: deoptimize; a box used again in its block is not decoded; a site whose feedback shows Floats and never two SmallIntegers has no SmallInteger path, two SmallIntegers deoptimize; one without Float feedback of its own in a method whose arithmetic saw Floats has both paths, unless it reported receivers that are not numbers); `at: at:put: size basicSize` with bounds checks for pointer, byte and string objects; `basicNew basicNew:` of pointer objects in eden (header, class, nil fields inline; the send when eden or the allocation sample's limit is reached); `== ~~ class`, `Character value`, `Character value:`; `value value: value:value:` of a closure the IR does not know: the block stub (its unit if it has one). Interrupt checks at method entries and backward jumps; the write barrier inline, left out for stores of immediates, nil, true and false; immutability checked once per object and block.

**Passes** (`OptPasses`): unreachable blocks, trivial phis, global value numbering over the dominator tree (guards, arithmetic, comparisons, Float conversions, constants; field loads within a block with no store or safepoint between), unused pure nodes, critical edges split, reverse postorder.

**Registers** (`OptRegalloc`): linear scan (Poletto and Sarkar) over one interval per value: x0–x13, x26–x28, doubles d16–d31 (never spilled, never live across a safepoint); a value live across a safepoint also has a home slot in the frame (an argument's is its own slot), stored at its definition and reloaded after the safepoint; constants are rematerialized. Phi moves are sequentialized (cycles through a scratch register).

**Code and frames** (`OptCodegen`). An optimized frame is a frame: x19–x22 as in the lower tier, the root activation's arguments in their slots, then home slots and the outgoing receiver and arguments; its `pc` is the bytecode size plus a safepoint number (stored at its own safepoints, derived from the return map in calls). Method and block units start with the entry of calls as baseline code makes them, then the prologue for callers that pushed the frame. Out-of-line paths after the code: guard failures, interrupt checks, store barriers, deoptimization after a call, resumption after a call (the interpreter returned into the frame: the result from its slot), the stack check, the bottom frame's return. The header holds the safepoint table, the deoptimization records (kind, the send, per activation method, closure, receiver, pc and the location of every slot: register, slot, constant, sunk closure), the dependencies, the inline caches and the return map; an oop pool after the code (pc-relative loads, GC roots), then the inline caches' literals. The listing (`machineCodeFor: #opt`) shows the root method's bytecodes and the inlined activations' pcs.

**Deoptimization** (`OptRuntime`). A failed guard jumps to a stub that saves the registers; the record rebuilds the activations as frames (the closures never made are made), the interpreter continues the innermost one, and the site's feedback learns what failed. A failure the feedback had not reported, or one in code compiled before the site's feedback last changed, invalidates the code at once (it compiles differently next time), so does the ninth deoptimization; a site that fails again in code compiled with what it reports now is marked: no speculation there next time; a unit is compiled at most 32 times. `materializeAll` (process switches, `thisContext`, the debugger) turns an optimized frame into a Context per activation; the interpreter returning into an optimized frame resumes it at its safepoint. Invalidation (lazy): a method added or removed for a selector the code inlined or speculated on (`flushCacheForSelector:`), become of a method: the code is marked dead, frames running it deoptimize when control comes back to them (a check after every call), calls into it go to the lower tier. Switching the mode away from `opt` makes every optimized frame Contexts first.

**Stress.** `--jit-flags eager` optimizes at the first count; `deopt` makes optimized code take every 37th slow path it passes (guards, interrupt checks, returns from calls) and deoptimize there, without feedback. `make test-jit` runs the image's tests under `--jit opt` with eager and with eager,deopt; `vm/tests/run.sh` the mini kernel's under both (with the GC stress) and the default thresholds; `JitOptRuntimeTest` covers deoptimization of a failed speculation (and none where nothing was speculated: `perform:`, `doesNotUnderstand:`, SmallIntegers beside Floats, BoxedFloat64s), invalidation of inlined code while it runs, closures that store temps across loops, closures a loop's unit inlines from its frame, calls into machine code (no sends through the runtime: `optRuntimeSends`), process primitives that switch no process, a count shared with a method that failed to compile, the stress, the listing.

**Flags** (`--jit-flags`, all on by default): `inline` (methods), `blocks` (closures), `prims`, `unbox` (Floats on doubles), `calls` (direct and block calls), `alloc`, `gvn`; `eager` and `deopt` are off.

Not done: loop-invariant code motion, range analysis and bounds-check elimination, escape analysis beyond closures, unboxed Floats across safepoints, inlining of closures made elsewhere (passed in: called through the block stub).

## Machine code

Package `VM-Jit` (layer 0), shared by both compilers:

- **`Arm64Assembler`** (Lowtalk module, translated with the JIT). `asm beginAt: start limit: end`, one message per instruction with operands in assembly order, `asm finish` (an `ASM_*` error code; the first error sticks). Registers, conditions, shifts, extends and barriers are class variables of `Arm64Module` (subclass it to use them): `X0`–`X30`, `XZR`, `SP`, `W0`–`W30`, `WZR`, `WSP`, `D0`–`D31`, `COND_EQ`…, `SHIFT_LSL`…, `EXT_SXTW`…, `BARRIER_ISH`…; the width (W/X) comes from the destination register, FP forms from D registers (`ldr: D0 base: X1 offset: 8`). Selectors: `add:with:imm:` (also `adds sub subs`, `cmp:imm:`, `cmn:imm:`; lsl #12 and negative immediates chosen automatically), `add:with:with:` `…shift:amount:` `…extend:amount:`, `neg:with:`; `and orr eor ands bic` `:with:imm:` (bitmask immediates) and `:with:with:[shift:amount:]` (also `orn eon bics tst mvn`); `mov:with:`, `mov:imm:` (shortest movz/movn/movk or orr), `mov:imm64:` (fixed four instructions, patchable), `movz/movk/movn:imm:shift:`; `lsl lsr asr ror` `:with:imm:` and `:with:with:`; `mul madd:…add: msub:…sub: smulh umulh sdiv udiv clz`; `csel csinc csinv csneg` `:with:with:cond:`, `cset:cond: csetm:cond: cinc cinv cneg:with:cond:`; `ubfx sbfx ubfiz sbfiz bfi bfxil` `:with:lsb:width:`, `ubfm sbfm bfm`, `sxtb sxth sxtw uxtb uxth`; `ldr str ldrb strb ldrh strh ldrsb ldrsh ldrsw` `:base:offset:` (scaled, else unscaled) `:base:preIndex:` `:base:postIndex:` `:base:index:[extend:shift:]`, `ldur stur …`, `ldp stp` `:with:base:offset:/preIndex:/postIndex:`, `ldr:label:`; `adr:label: adrp:label:`; `b: bl: b:if: cbz:to: cbnz:to: tbz:bit:to: tbnz:bit:to: br: blr: ret ret:`; `nop brk: dmb: dsb: isb`; `fmov:with: fmov:imm: fadd fsub fmul fdiv` `:with:with:`, `fsqrt fneg fabs frintm frintp frintz frintn scvtf ucvtf fcvtzs` `:with:`, `fcmp:with: fcmpZero: fcsel:with:with:cond:`. Labels: `newLabel`, `bind:`, `labelAt: anAddress`; forward branches are patched at `bind:`. Encoders: `logicalImmediate:width:`, `fmovImmediate:` (-1 if not encodable). Patching: `patchBranchAt:to:`, `branchTargetAt:`, `patchMov64At:value:`, `mov64At:`. Notes for annotated disassembly, recorded only after `recordNotes: true`: `comment:`, `comment:with:`, `bytecode:`. With constant operands an instruction is one store of a constant word and a limit check; emission runs at about 3·10^8 instructions/s (`Tests-VM/JitSample` with the argument `bench`, cc -O2, M2 Max).
- **`CodeCache`** (Lowtalk module): `openWithSize:` (one `MAP_JIT` mapping), `allocate:`, `keep` (what is allocated survives flushes), `flush`, `beginWriting`, `endWritingFrom:size:` (`pthread_jit_write_protect_np`, `sys_icache_invalidate`, bound in the library `DarwinJit`), `endWriting`, `invalidate:size:`. Code is called by casting its address: `(self cCoerce: entry to: 'int64_t (*)(int64_t)') call: 42`.
- **`Arm64Disassembler`** (image): `textFor:at:` prints as LLVM's objdump does; `listingOfWords:at:annotations:` prints a listing with `Arm64CodeAnnotations` (bytecode headers, comments, labels for branch targets, symbol names for calls).
- **`JitRuntime`**, **`BytecodeAnalysis`** (VMCoreModules), **`JitCompiler`**, **`JitStubs`** (Arm64Modules), **`JitPrimitives`** (`jitParameters`: `Smalltalk vm jitParameters`, `jitMode:`; `jitCode`): the shared runtime, part of the VM.

The simulator runs the VM without the JIT: machine code does not run there (`CodeCache>>canRunCode`), so `JitRuntime>>start` turns it off, whatever `--jit` says.

Tests (`Tests-VM`): encodings against the system assembler's (`Arm64Reference`, generated by `tools/arm64-reference.py`), simulated and compiled with cc; disassembly against objdump; `JitTest` runs `JitSample` natively; `JitRuntimeTest` covers on-stack replacement, redefinition and become while machine code runs, literals in the code, process switches, deep recursion, code cache flushes and the listing under `baseline`, `JitOptRuntimeTest` the same under `opt`; `JitBaselineTest` the baseline's inline caches through their states, relinking, unboxed Floats when Smalltalk runs in a slow path, non-local returns, allocation and every ablation flag. `vm/tests/run.sh` runs the mini kernel's tests also under `--jit baseline` and under `--jit opt` (eager; eager,deopt) with `--jit-threshold 0` (with the GC stress) and the default thresholds; `make test-jit` the image's tests under `none`, under `baseline` and under `opt` (eager; eager,deopt) with `--jit-threshold 0`, Tests-Kernel also under `opt` with a 1 MB cache that keeps notes (it is flushed again and again).

## Benchmarks

- **Are We Fast Yet** (Marr et al., DLS 2016): Bounce, CD, DeltaBlue, Havlak, Json, List, Mandelbrot, NBody, Permute, Queens, Richards, Sieve, Storage, Towers. The same sources also run on Pharo 12 (Cog), the reference ceiling.
- The micro suite (`vm/tests/bench`), and real workloads: recompiling the image's sources, text rendering.
- Per benchmark: every iteration's time (warm-up curve), steady state (median of the last half), JIT time and code size.

## Comparison

Every design measured on the same benchmarks (`vm/tests/bench/results`): AWFY geometric mean of the steady state (median of the last half of the iterations, median of 3 invocations) relative to the interpreter and to Pharo 12; compile time and code size per bytecode compiled over the AWFY runs (for `opt` its optimizing compilations, inlined bytecodes included). The ratios of each row come from one run interleaved with `none`: template, threaded and stencil from `samaltak-cp-{none,template,threaded,stencil}-2026-10-24-*.csv` (10 iterations; Pharo 12 from `pharo12-cog-2026-10-24-*.csv`), the others from `samaltak-{none,baseline,opt}-2026-10-25d-*.csv` and `pharo12-cog-2026-10-25d-*.csv` (30 iterations); default thresholds.

| design | what | AWFY / `none` | AWFY / Pharo 12 | µs / bytecode | bytes / bytecode |
|---|---|---|---|---|---|
| `none` | the interpreter | 1 | 2.63 | – | – |
| template | a fixed machine-code template per bytecode on the frame's slots, sends through the runtime | 0.75 | 1.93 | 0.17 | 37 |
| threaded | call threading: a `bl` per bytecode into its handler, C compiled into the VM | 1.21 | 3.14 | 0.12 | 15 |
| stencil | copy-and-patch: handler stencils compiled by cc, copied and patched | 0.86 | 2.24 | 0.15 | 68 |
| `baseline` | Cog-style: inline caches, operands in registers, inline arithmetic and primitives | 0.24 | 0.64 | 0.20 | 43 |
| `opt` | baseline code plus the optimizing tier | 0.15 | 0.40 | 3.6 | 75 |
| Pharo 12 | Cog, the same sources | 0.38 | 1 | – | – |

- Removing the interpreter's dispatch alone (template) gives 0.75×; a call per bytecode (threaded) costs more than the dispatch; the stencils (1.16× template) keep the operand stack's top in a register where the template knows every slot's offset. `baseline` beats Pharo 12 on every benchmark, in the steady state and in the first iteration (0.62); `opt` (0.63× `baseline`) more so (first iterations 0.50).
- Ablations (one flag off, AWFY geometric mean of the steady state relative to all on; `samaltak-jit-baseline-no-FLAG-2026-10-25-*.csv`, `samaltak-opt-no-FLAG-2026-10-25d.csv`): `baseline` `ic` 5.56, `arith` 1.44, `regs` 1.34, `barrier` 1.26, `mega` 1.25, `prims` 1.22, `blocks` 1.13, `float` 1.08, `access` 1.07, `quick` 1.07, `pic` 1.06, `fuse` 1.05; `opt` `inline` 6.48, `prims` 2.52, `unbox` 1.41, `calls` 1.37, `blocks` 1.27, `alloc` 1.23, `gvn` 1.08.
