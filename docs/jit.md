# JIT

Two compilers on a shared runtime: `baseline` (Cog-style) and the optimizing tier `opt`, whose lower tier is baseline code. Both are written in Smalltalk: Lowtalk for code in the VM (translated to C like the rest of it), ordinary Smalltalk for code in the image. No LLVM at run time. Targets: Apple Silicon (M2 Max, arm64, macOS; also Linux on arm64, e.g. Asahi) and x86-64 Linux (x86-64, below). Both beat Pharo 12's Cog JIT on every Are We Fast Yet, micro and real-world benchmark (Comparison, docs/benchmarks.md).

| `--jit` | what |
|---|---|
| `none` | the interpreter (computed goto, PGO) |
| (all) | Contexts married lazily: closures, `thisContext` and exception handling do not flush frames (in the interpreter, for every mode) |
| `baseline` | Cog-style: own assembler (arm64, x86-64), simulated operand stack in registers, machine-code inline caches (monomorphic, polymorphic, megamorphic), inline SmallInteger/Float arithmetic and common primitives |
| `opt` (default) | baseline code plus an optimizing tier in the VM (Lowtalk): SSA IR, inlining from type feedback, closures not made, unboxed Floats, linear-scan register allocation, deoptimization to frames |

Each compiler has ablation flags (`--jit-flags -ic,-arith,...`) so that the effect of each optimization is measured separately.

## Shared runtime

The interpreter's frames are the canonical state. Machine code runs on the same frame records and C-stack slots; at every safepoint (a call out of machine code that may allocate, collect, flush frames, switch processes or run Smalltalk) the values it holds in registers are in their slots and the frame's `pc`/`sp` are valid. Hence:

- the interpreter can resume any frame of compiled code at its bytecode pc, and compiled code can be entered at the pc of a frame the interpreter was running (on-stack replacement at backward jumps, return into a compiled caller);
- GC roots, `materialize_all` (frames into Contexts), the debugger, stack printing and process switches stay as they are;
- deoptimizing baseline code is free; flushing the code cache only needs no machine code on the native stack.

**Frames.** A `Frame` has a `code` field: its method's `JitMethod` (machine code), 0 (none), or 1 to 0xFFFF while the JIT counts it (activations, then backward jumps). Every frame push sets it: from the method cache entry (`K_JIT` entries hold the code or 1, as `JitRuntime` answered when `fillCache` filled them: installing code leaves the caches alone, an activation through an entry that still counts finds the code compiled since, one through baseline code the optimized code the method has by now, `JitRuntime>>best:`), for blocks from the home method's code. Machine code keeps `pc` and `sp` (one 64-bit store) current at safepoints instead of `ip`; the runtime turns them into `ip`, `nframes` and `cstackUsed` (`Interpreter>>syncFrame:`). Operands live in their slots at offsets known at compile time (`BytecodeAnalysis`: the depth before every instruction).

**Native stack.** Machine code calls compiled callees with `blr` and returns with `ret`, so the native stack mirrors the frames entered since the last `jit_enter`, 16 bytes (x29, x30) per activation. `jit_enter(frame, address)` (`JitStubs`, generated at startup) saves the callee-saved registers, sets x19–x22, remembers the native stack pointer, pushes x29/x30 as a prologue would and branches to `address`. Leaving to the interpreter resets the native stack to `jit_enter`'s and returns: `exitSync` (the code stored the frame's pc and sp: the interpreter continues there), `exitPlain` (the runtime made the frames canonical). Returning from the first activation lands in the trampoline, which answers the caller's frame; the runtime continues its machine code if it has some (`JitRuntime>>run:at:`), else the interpreter.

**Registers** (callee-saved, pinned): x19 the frame record, x20 its slots (`fp`, receiver at `fp[-1]`), x21 the receiver, x22 the `JitState` (nil/true/false and the classes inline paths check, refreshed after every GC; the interrupt flag; the frames array; jit_enter's stack pointer; the young space's bounds). x23–x25 hold nil, true and false, x26–x28 baseline code's loop temps or opt's registers; x0–x17 scratch. x18, the platform register on macOS, is one more loop temp or opt register on Linux and UEFI (`Arm64Assembler>>hasX18`, a constant of the C compiler's, `Arm64Abi`); a temporary of C's, it is reloaded after calls as the other loop temps are, and the stubs that keep the registers (remember, the copy stub's memmove) keep it. Code entered by a caller that pushed its frame (the runtime's sends, optimized code calling baseline code) starts with the prologue (`JIT_PROLOGUE_BYTES`: x19 := the next Frame, push x29/x30, load x20, x21); its start is after the prologue.

**Calls into the runtime.** Machine code stores pc and sp, calls a stub (`ldr x16, =function; br x16`, in the code cache so that `bl` reaches it) with the frame in x0; after a safepoint it reloads x21. The runtime answers 0 (continue), 1 (leave: `exitPlain`) or, for a send, the callee's entry (frame pushed; the caller `blr`s it). If frames were flushed or moved (process switch, stack full, `terminateTo:`), or code was invalidated, it answers 1. Sends through the runtime (`OptRuntime>>send:index:site:` for optimized code's calls that no machine code takes, `JitRuntime>>dispatch:frame:argc:`) use the interpreter's inline caches, keyed by the site's code address: frameless sends (^ivar, constants, setters) touch the frame only when an interrupt is pending (they are safepoints, as in the interpreter); leaf primitives and primitives run as in the interpreter; a method with code gets its frame pushed from the cache entry; a method without code is counted (compiled at the threshold) or its frame is pushed and the interpreter runs it; `perform:` sends its selector, the arguments moved down over it as the primitive does, and a selector not understood sends `doesNotUnderstand:` with a Message of it and the arguments, as the interpreter does; a send the runtime cannot complete cleanly (a full stack; a `perform:` whose primitive fails, of a selector not understood or of `perform:`) leaves to the interpreter to execute it again, which it can because nothing happened yet. Special selectors first try the interpreter's fast paths, `value`/`value:` on blocks enter the block's code. Arrays (`0x94`) of more than 64 elements are runtime calls, smaller ones and closures when eden is full.

**Interpreter hooks.** Activating a method whose cache entry is `K_JIT` (count, compile, enter at start: `JitRuntime>>activated:`), returning or non-locally returning into a frame with code and activating a block whose home has code (continue at `ip`: `resume:`), a backward jump in a frame whose `code` is not 0 (count, compile, on-stack replacement: `backJump:`). Process switches flush all frames, often (the sampler), so switching to, returning into or jumping back in a Context whose method has code marries the Context to a new bottom frame, its sender the base, and continues it in machine code (`resumeContext:`, `run:at:` after machine code switched, `Interpreter>>thawFor:`; the interpreter otherwise, if the method has no code or the pc is no resumption point); otherwise long-running loops would stay interpreted and every return into them would leave machine code. With `--jit none` they cost a load and a branch on paths that already do work. The bytecode-pc to machine-pc map holds the resumption points: method and block starts, continuations after sends, loop heads, conditional jumps (a `mustBeBoolean` send returns to them).

**Exits.** A compiler may leave to the interpreter at any instruction (`exitSync`): baseline code does for non-local returns, `mustBeBoolean`, stores into immutable objects or into a married Context's fields, and returns from the bottom frame. The interpreter continues the frame and comes back at the next send, return or backward jump.

**Code.** One `MAP_JIT` region (`pthread_jit_write_protect_np`, `sys_icache_invalidate`), bump allocated after the stubs; it takes the place of a zero-fill array in the VM's image (`CodeCache`), near the VM's data, so that `adrp` from the code reaches it (tiering counters, type feedback, eden's top, call caches). A compiled method's header (`JitMethod`) follows its code: the method (a GC root), the compiler, start, the bytecode map, the notes. Methods are found by identity hash (stable across moves) in a 64K open-addressed table; activations are counted per hash. Scavenges update the methods of headers compiled while the method was young (a list); full GCs and become all of them. Literals are in the code: baseline code's literal pool, optimized code's oop pool (GC roots). When the cache (or the table) is full the method stays interpreted and the whole cache is flushed at the next interpreter hook, when no machine code is on the native stack: frames go back to counting, the method caches are flushed. Become of a compiled method kills its code (its frames are interpreted from then on). Method dictionary changes flush the interpreter's caches, which the runtime's sends use. Snapshots flush the frames; machine code is not saved.

**Triggering.** `--jit-threshold N`: activations before a method is compiled (0: the first); `--jit-osr N`: backward jumps in an interpreted frame before its method is compiled and the frame continues in machine code. `--jit-cache MB` (1–128).

**Disassembly.** The machine code of any method can be shown from the image, for either compiler (compiling it if needed, `CompiledMethod>>machineCode`, `machineCodeFor: #baseline`, the System Browser's method menu): every instruction, grouped under the bytecode it implements (with the source line), and commented with what it does (tag check, overflow branch, spill, call into the runtime by name...). Compilers record the comments as they emit (always for a disassembly, for all code with `--jit-flags notes`; a copy compiled for a disassembly is dropped and leaves the feedback alone); `jitCode` answers code, address, bytecode map, notes and stub names; `Arm64Disassembler` or `Amd64Disassembler` (by `Smalltalk vm jitArchitecture`) prints them.

**Profiling.** With `SAMALTAK_PERF_MAP` set, the runtime writes perf's map of JIT code, `/tmp/perf-<pid>.map`: the stubs, then each method's code as it is compiled (`bl:Class>>selector`, `opt:Class>>selector`, a block's or loop's unit with its pc) and each polymorphic inline cache (`JitRuntime>>openPerfMap`); `perf report` names samples in machine code by it. With `SAMALTAK_PERF_MAP=jitdump` it also writes perf's jitdump, `/tmp/jit-<pid>.dump` (each piece of code with its bytes and the time it was made; mapped executable on Linux, `JitPlatform>>mapForPerf:`, so that perf notes it): record with `perf record -k mono`, then `perf inject --jit` makes an ELF file of each and `perf annotate` disassembles them with the samples per instruction. Code is dumped as it was made: inline caches linked and PIC cases added later are not in it. Measurements: Where the time goes.

**Statistics** (`vmStats`, `VMStatistics`): methods and bytecodes compiled, microseconds compiling, code bytes, cache flushes, entries into machine code, exits, resumptions, on-stack replacements, methods that could not be compiled.

**Constants.** The code generators (`JitStubs`, the compilers) are `Arm64Module`s, so they name registers and conditions; the runtime and the analysis are `VMCoreModule`s, with the VM's helpers and constants. Neither needs the other's class variables: the generators ask the runtime through inline accessors (`runtime arith`, `runtime prologueBytes`), struct offsets come from the structs (`(self cCoerce: 0 to: 'Frame *') fieldAddress: #fp`).

## Compilers

`JitRuntime>>compile:mode:notes:` analyzes the method (`BytecodeAnalysis>>analyze:`), then has the mode's compiler emit at the assembler's pc; it appends the header, installs it and counts. A new compiler:

- a module subclassing `JitCompiler` (its conventions: prologue, `emitSync:depth:`, stubs, frame and state offsets) with `compile: aMethod` answering whether it emitted every reachable instruction; it records resumption points (`runtime noteResume:at:`);
- its mode in `JitRuntime>>modeNamed:` / `modeName:` and a case in `compile:mode:notes:`; its flags in `flagNamed:length:` (queried as inline accessors);
- if it keeps values in registers, spills before every runtime call and at every resumption point.

**Baseline** (`JitBaselineCompiler`, `JitBaselineRuntime`, `--jit baseline`). After Cog's StackToRegisterMappingCogit: one pass over the bytecodes with a simulated operand stack whose entries are in their slot, in a register (x0–x8, x12–x15), a constant, nil/true/false (pinned in x23–x25), self (x21), a temp or a literal not loaded yet, or an unboxed Float (d8–d15). Values go from producer to consumer in registers, constants become immediates, folded where both are known; the stack goes to its slots at sends, runtime calls and merge points (which start with every entry in its slot). Before an instruction that may send, everything below its operands is written back (unboxed Floats stay: its slow path boxes and reloads them around the send), so its slow path stores only the operands. An innermost loop that makes no closures, Arrays or `thisContext` keeps its most used temps (up to 3, 4 where x18 is free, each used more often than the loop sends) in x26–x28 and x18 too, stored through to their slots and reloaded after every call out of it (sends, slow paths). Layout: checked entry, unchecked entry, frame code, the bytecodes in pc order (block bodies with their entries), slow paths, resumption stubs, the literal pool, the `JitMethod` header (`adr` reaches it).

- *Sends*: the receiver in x0, receiver and arguments in their slots, `add x20` to the callee's fp, `ldr x9` the site's class from the pool, `bl` the site's target, `sub x20` after; the result comes back in x0. The target is the miss stub while unlinked; a compiled method's checked entry when monomorphic (its class check against x9: tag test, class word, compare; immediates by tag out of line); a `BaselinePic` of up to 6 classes, each branching to its target's unchecked entry; or, megamorphic, the megamorphic stub (x9 then holds the selector; a 4096-entry table of 2-entry sets by the addresses of class and selector, probed in machine code: two pairs that meet keep both). The miss stub calls `JitBaselineRuntime>>miss:receiver:ret:`, which looks the send up (the interpreter's global cache), compiles the target at the threshold, links or relinks the site (code patched under the W^X toggle) and jumps to the target; it leaves to the interpreter for `doesNotUnderstand:` and uncompiled targets. Young classes are cached too (their words become young roots). Method dictionary changes (`flushMethodCache`, `flushCacheFor:`), become and dead code unlink every (or every such) site. Super sends link once to the unchecked entry. Each site's state is its type feedback: `JitBaselineRuntime>>feedbackSitesOf:` and friends (pc, selector, state, receiver class and target per case), `CompiledMethod>>jitSendSites` in the image.
- *`perform:`* (Cog's `genPrimitivePerform`): `perform:` up to `perform:with:with:with:with:` and `perform:withArguments:` (an Array) are compiled; their primitive probes the megamorphic table with the receiver's class and the selector, checks the entry's fourth word (the selector's argument count; -1 for a perform method: the interpreter does `perform:` of `perform:`), moves the arguments down over the selector (the Array's elements: unless the sender is married, not optimized, and its Context would not hold them, as the interpreter's `activeCapacity`: a C primitive target may flush the frames) and branches to the target's unchecked entry. A miss calls `performMiss:receiver:ret:info:`, which fills the table and enters the target, answers that the primitive failed (the method's body runs) or leaves as `miss:` does. The send of a callee entered so cannot be executed again: until its frame exists the runtime takes its sender as past the send (`setTop:ret:fp:argc:`), and a full stack is caught before the arguments move.
- *Frames*: the callee compares its fp against the JitState's stack limit (0 while an interrupt is pending: the one compare is also the interrupt check; `entrySlow:ret:callee:` takes the interrupt with the callee's frame pushed, popped again if no process switched), pushes the native record (x29, x30) and its Frame with two `stp`s and a `str` (code, closure and ctx nil, fp, pc and sp 0), x21 := the receiver, nil into its temps; a return pops both after one check (a married frame, or frame 0, which `run:at:` marries, takes the slow path). A Frame's method, pc, sp, ip and lits are lazy: the runtime makes a suspended frame canonical from the return address in its callee's native record (`canonicalizeBelow:`, the method's return map: return offset, pc, depth, argc, length, pushes; frame f's record is at `baseRecord − 16·(f − baseFrame)`), top down, stopping at the first frame that already is (a zero pc marks a frame pushed since). Every runtime entry that may collect, flush or leave does that first (`JitRuntime>>sync:`, the exit stub).
- *Quick methods* (^ivar, ^self, ^constant, ^literal, setters) run without a frame; with an interrupt pending they take the frame's path (sends are safepoints). *Primitives* run before the frame: in machine code for `basicNew`, `basicNew:` (eden bump allocation; no identity hash, which its first use assigns: `identityHash` in machine code calls the C primitive while the header has none), `==`, `class`, closure `value` and `valueWithArguments:` (the Array's elements copied over it into the block's arguments, if its frame has room), SmallInteger and Float arithmetic and comparisons, SmallInteger `quo: rem: // \\`, `sqrt`, `truncated`, `charValue`, `Character value:`, `identityHash`, `at: at:put: basicSize` (pointers without fixed fields, 32-bit words, bytes), String `at:` and `at:put:` (Characters in bytes and 32-bit words), `uint32At:` and `uint32At:put:` of bytes, `replaceFrom:to:with:startingAt:` of bytes, 32-bit words and pointers without fixed fields from an object of the same kind (the copy stub: up to 16 bytes the first and the last 8, 4 or 2 loaded before either is stored, up to 32 the first and the last 16 and up to 64 the first and the last 32 in pairs of d registers (`ldp`/`stp` of d0–d7, on x86-64 `movsd`), all loaded before any is stored, memmove beyond; an old pointer receiver not remembered yet goes to the C function, which remembers it); the others through their C function: `<leaf>` ones called directly from the method's entry (`leafPrim:fn:argc:`: the interpreter's primitive plumbing set as its own leaf calls set it, no frame made canonical, no epoch or invalidation check: a leaf primitive neither allocates, collects, switches processes, looks at Contexts nor invalidates code; it answers or fails, anything else is fatal; its result, or 0 for a failure, back in x0), the others through the primitive stub (`prim:fp:fn:info:`). Failure continues into the frame and the body.
- *Inline at send sites*: SmallInteger `+ - * // \\ bitAnd: bitOr: bitShift:` and comparisons (tag checks only for operands not known, immediates, overflow branches), compare and branch fused with the conditional jump (a loop's bottom is one branch back to its head, where loops check for interrupts), jumps threaded into a conditional jump on the value just pushed (`and:`, `or:`). Floats: an operation with an operand that surely is a Float (an unboxed value, a Float constant, a temp whose unboxed value is known in the basic block) decodes the other (SmallFloat64, BoxedFloat64, SmallInteger) and leaves its result unboxed in a d register for the next one; other operations try SmallIntegers first, Floats out of line (SmallFloat64s straight through, the same temp twice decoded once); boxing (a SmallFloat64, else a BoxedFloat64 from the runtime) happens when a value goes to memory or a send. `== ~~ class` never send, nor do `isNil notNil` while only UndefinedObject and ProtoObject define them (a heap scan; another definition drops all code); `at: at:put:` inline for Arrays, out of line for Strings, Symbols and ByteArrays (`size` is sent: classes define their own, and Arrays answer it from the primitive in machine code); `value value: value:value:` check the closure's class and argument count and call the block stub, which finds the block's entry in a (home method, startpc) cache. Closures are allocated in eden, and with the first a frame makes, its Context (the frame married; eden full: the runtime makes them; the frame's return widows a young one inline, copying its slots into it as `Interpreter>>widow:` does, frame 0 and an old one through the runtime), so are Arrays (`0x94`) of up to 64 elements; outer temps inline; the store barrier's fast path inline (the remember stub saves the registers).
- *Non-local returns* leave to the interpreter.
- *Contexts*: `thisContext` calls the runtime, which marries the frame. 0x81 of `sender`, `pc` or `stackp` (Context's methods) loads the field unless the receiver's `sender` is a SmallInteger, a married Context: then the runtime answers it from the frame (`contextField:`; if that flushed, the interpreter executes it again). 0x88 is 0x85 with that check too: a married receiver leaves to the interpreter.
- Resumption points: method and block starts (an interrupt check out of line), loop heads, send continuations (a stub loads the result from its slot) unless unboxed values are live there. Exits go through the runtime so that the frames below become canonical.
- Flags (each switches one optimization off, for the ablations): `ic` (inline caches: every send looks up in the runtime), `pic`, `mega`, `regs` (every push to its slot), `arith`, `fuse` (compare and branch, jump threading), `float`, `access`, `prims`, `blocks`, `quick`, `barrier`, and `notes`.

## Optimizing tier

`--jit opt` (`OptBuilder`, `OptPasses`, `OptRegalloc`, `OptCodegen`, `OptRuntime`, `JitFeedback`; Lowtalk in `VM-Jit`). Baseline code is the lower tier; hot methods, blocks and loops are compiled again from their bytecodes with type feedback, inlining and speculation, and deoptimize to frames when a speculation fails.

**Tiering.** In this mode baseline code counts, per method (identity hash), method and block entries and backward jumps (`emitTierUp:depth:loop:`, a decrement of a word in the VM's data). At zero it stores pc and sp and calls the tier-up stub (x0 the frame, x1 whether at a backward jump); `OptRuntime>>tierUp:loop:` answers where the frame continues: the method's optimized code at its start, a block's unit, or a loop's unit (on-stack replacement at the loop head). Units are compiled once per method, per block (method, startpc) and per loop (method, block, loop head); a loop has a plain unit and up to 16 variants, each for one signature: a 32-bit hash of the code of the closures other frames made that the frame holds and of where they are (Inlining; `closureSignatureOf:`), and of the receiver's class where the method is inherited (`signatureOf:method:`). A frame enters the variant of its signature (a new one while the loop has fewer than 16 and none that failed to compile, and there are fewer than 2048 variants in all: after that loops use their plain unit until the code cache is flushed); without one, or if it failed, the plain unit, which inlines no such closures. A loop of a unit entered at its start (a method's or a block's) whose turns call a closure the unit did not make (through the block stub: a block passed in) counts its turns in the activation (a phi, `OptBuilder>>turnAt:`); at the 1000th (`OPT_RESPEC_TURNS`) its interrupt check calls the runtime (`OptRuntime>>respecialize:`): if the activation running the loop holds a closure another frame made that a variant may inline, and there is room for variants, the frame's activations become frames there (the unit stays) and that method counts one backward jump, so the loop's next turn enters its variant; once per activation, without a flush (`do:` over 3 million elements from code that is not optimized: 10.2 to 2.0 ms, `inject:into:` 21.9 to 2.0; `--jit-flags -respec` turns it off). A failed compilation is remembered. Methods whose hashes meet share a count: it starts over at every tier-up, whatever the outcome. A method's optimized code is found by the activations through the method caches (`best:`) and installed over its baseline code's unchecked entry: a `b` to an entry that builds the frame as baseline code builds it (`JitBaselineRuntime>>redirect:to:`, undone on invalidation; not for quick methods and primitives); a block's unit is what the block stub enters from then on (its cache is cleared). `--jit-opt N` sets the count (default 1000), `--jit-flags eager` makes it 1. Frames resumed after a process switch (Contexts married to new frames) enter loop units too, after `--jit-osr` backward jumps in the lower tier: flushing an optimized frame (`OptRuntime>>materialize:`) sets its outermost method's count to that (at most the full count), so a hot loop leaves its unit only briefly while a loop that turns once per wake-up of its process (the timer process's) stays in baseline code, whose frames flush for less; if their code makes closures, the temps the closures reach stay in the frame (a closure may change them through the Context).

**Background compilation** (`OptRuntime`, the flag `bg`, on by default). A tier-up that asks for a unit builds its IR on the VM's thread (`frontEnd:`: the builder reads methods, classes, literals, the type feedback and, for a loop's unit, the frame) and takes what the passes would read of the heap and the feedback (`OptIR>>snapshot`: the profile bits at every node's and frame state's bytecode, the class of every constant); from there on the passes and the register allocator (`backEnd:`) touch nothing but the IR and their own arrays, and a helper thread runs them while the frame goes on in baseline code. Code generation and installing stay on the VM's thread: the assembler, the code cache, the bytecode analysis and the inline caches are the baseline compiler's too. An IR of fewer than 256 nodes (most units, a sixth of the back end's time) is cleaned up, allocated and installed at once instead: some 15 µs, less than waiting for a later tier-up costs. One job at a time: a tier-up while the helper has one is deferred (its count set to at most 64), the job's own unit's too, which so asks again soon. At a tier-up after the helper finished (`bgPoll`) the job is installed if what it was built on still holds: no GC that may have moved an object it names (a full GC or become; a scavenge if it names a young object, `bgMentionsYoung`), no invalidation (a method dictionary change, become, `changeClassTo:`, a mode or flag change), no flush, its method's lower-tier code still the one it was built for and its unit still without code (`bgValid`); its code is then generated from the allocated IR and installed as a synchronous compilation's (stamped with the feedback's stamp when it was built). Else it is dropped. A unit whose job a GC dropped, or whose back end failed where a synchronous compilation tries again without twins on doubles, is compiled on the VM's thread at its next tier-up. Any other optimizing compilation on the VM's thread (a copy for a disassembly, a synchronous one) first waits for the helper and drops its job. Where there are no threads (UEFI), where the VM may run on one CPU only (taskset: `sched_getaffinity`), with `SAMALTAK_OPT_TRACE` or with `-bg`, the VM's thread compiles everything as before. `SAMALTAK_OPT_BG_INLINE` runs the back end on the VM's thread at the tier-up and installs at a later one, as the helper's (the deferred installation without a thread, for debugging); `SAMALTAK_OPT_BG_TRACE` prints installs and failures. Statistics: `optBackgroundJobs`, `optBackgroundDiscarded`, `optBackgroundMicroseconds` (the helper's; `optCompileMicroseconds` is the VM thread's), `optBackgroundDeferred`; `jitParameters`' seventh element is the helper's state (-1: none), a fifth element true or false of its argument holds finished jobs (tests). On the X925 (`awfy.sh --cpus big`, 10 laps, `bg` against `-bg`, two invocations each) AWFY's first laps take 0.94 of the time (geometric mean; the first three 0.96, all ten 0.97): DeltaBlue's first 71 to 42 ms, CD's 52 to 40, Json's 32 to 25, Havlak's 86 to 80; the steady state is the same.

**Calls between the tiers.** Optimized code calls as baseline code does: receiver and arguments in their slots, the receiver in x0, x20 the callee's fp, `bl`, the result back in x0. A method it knows (the receiver's class known or guarded) it calls at its baseline code's unchecked entry (a primitive's machine code first; optimized code through the redirection), a closure it did not make through the block stub (after its argument count), anything else through an inline cache of its own, which `JitBaselineRuntime>>miss:receiver:ret:` links as baseline code's (monomorphic, polymorphic, megamorphic; unlinked with them). What baseline code leaves to the interpreter for (`doesNotUnderstand:`, a method not compiled yet; a `perform:` the machine code does not do) the miss handler sends through the runtime (`OptRuntime>>sendFrom:ret:`), as the entry stub's slow path does for an optimized caller when the stack is full; the stubs continue where it answers (the callee's entry, its frame pushed, or a `ret`: the result is in the receiver's slot). Callees build their frames (optimized code's entry from such calls builds it as baseline code does), so an optimized frame suspended in a call is lazy too: its return map (return offset, safepoint, argument count) gives `canonicalizeBelow:` and `setTop:ret:mode:` its pc (bytecode size plus the safepoint) and sp. Optimized code answers in x0 and keeps x23–x25 (baseline code's nil, true, false; reloaded after runtime calls). A C primitive that commits its result without switching processes returns into the machine code that called it, into optimized code even if code was invalidated (the interpreter cannot continue its frame).

**Type feedback** (`JitFeedback`): per (method, bytecode pc) up to 4 receiver classes with counts, `FB_MEGA` beyond, and profile bits: Float operand, non-number operand, overflow, and why optimized code deoptimized there (class guard, arithmetic guard, bounds check, other). It does not depend on the compiler that collects it: baseline code reports every receiver class its inline caches miss on (`noteSend:pc:class:`) and, without a call, sets a byte per site when an inline Float path runs (`floatBitAddressFor:pc:`, bytes shared by hash: the optimizer reads one only at arithmetic with an inline Float path, `+ - * /` and comparisons, whose code clears it when compiled; at `bitShift: // \\ bitAnd:` it would be another method's Float); a SmallInteger that misses at arithmetic baseline code takes inline is one its inline path did not take, and the miss reports why (the argument a Float, or something else that is no SmallInteger, or the result overflowed); deoptimization reports what failed (an arithmetic guard looks at the operands, a class guard at the receiver, a superinstruction's too). What baseline code takes inline without a send gives no feedback; the optimizer reads that as the inline case: `at: at:put: size` as Arrays, unless the compilation knows better (a value a guard of it took for a class is taken for that class again; an outer temp of a closure the frame shows, for the class of what it holds now); a guess that fails deoptimizes once and reports the class it met: the next code has that case alone, and an Array's after another failure if Arrays come too, `value value: value:value:` as BlockClosures (both guarded), arithmetic as SmallIntegers (a site that reported other classes has no SmallInteger case, and deoptimizes on one, until some arithmetic of its method reported a SmallInteger: then all of them have it); `isNil notNil` are comparisons with nil while no class but UndefinedObject and ProtoObject defines them.

**IR** (`OptIR`): nodes in fixed arrays (operation, representation oop or double, type: SmallInteger with a range, Float, Boolean, nil, Character, a class), blocks with predecessor edges, frame states (per activation: method, closure, receiver, pc, slot values, chained to the caller's) for every guard and safepoint, inlined activations. `OptBuilder` builds SSA directly from the bytecodes (Braun et al., Simple and Efficient Construction of Static Single Assignment Form, CC 2013), one variable per frame slot of every activation; arguments are never phis, nor are temps that neither a loop nor a closure of their activation (which may be inlined into the loop) stores. A frame state names nil for a temp that no bytecode from its pc on reads before storing it (`BytecodeAnalysis>>analyzeLiveness`, a backward analysis of each method's and block's slots 0–63): such temps make no phis and keep no values alive, and a frame rebuilt from optimized code has nil in them (Smalltalk looking into it sees nil there). Always named: arguments, slots from 64 on, every slot an outer-temp instruction of the method names, all temps of a method with a primitive or `thisContext`, temps kept in the frame. A bytecode the builder decodes that reads a temp the analysis has dead prints `samaltak: liveness mismatch` and gives up the compilation.

**Inlining.** `perform:` of a constant selector the receiver's class understands is a send of it, inlined or called as any other; its arguments go a slot down, frame states at it keep the `perform:`'s slots, and deoptimization before its call puts the selector back (`SI_PERFORMED`). Other `perform:`s call the perform methods' machine code. A send is inlined for the class the receiver is known to have (a constant, or a phi's one value from the predecessors that can run: the scan builds the dead branch of a constant condition too), or speculated from feedback: one class behind a guard, up to four behind a type switch (between classes of objects the class loaded once, without a branch (an immediate reads a word of the JitState, which is no class), and compared with each, a load value numbering shares with other switches on the value; anything else deoptimizes; at an arithmetic site that saw Floats, which baseline code's inline paths report no class for, it is sent); a mega site, one that deoptimized for a class, and sends without feedback are inline caches; a method with baseline code that is not inlined is called at its unchecked entry (Calls between the tiers). A send without feedback that never ran deoptimizes instead (`unreached:special:pc:act:`), also where its receiver's class is known: an ordinary send (or `@ new new: max:`, which baseline code never takes inline) in a method whose baseline code was compiled since the feedback table was last cleared (`JitMethod` generation: its inline caches, linked since, reported every class they met), not with `eager`. So a cold path costs no call, inlines nothing, and the closures it would pass on stay unmade: `w timesRepeat: [...]` on a branch that never ran made the whole loop's unit fail (PNGWriter's `filteredInSmalltalk:...`, 261 to 106 ms). Taken, it deoptimizes as a type switch's other classes do: the receiver's class becomes the site's feedback (`FB_DEOPT_COLD` in the record), and the code is compiled again with that case; but the first time a site that had never reported is taken, in code that deoptimized fewer than three times, the code stays, and its method enters it again after `--jit-osr` backward jumps in the lower tier: a path taken once compiles nothing again. Its frame state names every temp of its activation, dead or not: such a deoptimization is not rare, and a temp no instruction reads again may be what keeps an object alive (WeakRegistryTest's registered objects). Methods up to 200 bytecodes, 3000 in all (in a unit whose root activation has loops, sends outside every loop only up to 1500 of them: straight code runs once a call, a loop's body many times, and the loops would otherwise call what straight code before them took the budget from; and a send leaves 300 to each loop head of the root activation after it, up to half the budget, so that an earlier loop does not take what a later one needs: `Planner class>>chainTest:`'s loop that builds the chain left the one that runs the plan calling `DBVariable`'s accessors, DeltaBlue 8.8 to 6.2 ms without the profiler's flushes, which sent the frame to that loop's own unit), 8 deep, a recursive one once. Blocks evaluated by an inlined `value…` send are inlined into the activation that made them; their closures are never made: frame states describe them (sunk), deoptimization makes them, marrying the frames they refer to. A closure that escapes (stored, passed, answered) makes the compilation start over without inlining the method that made it (if that method is not inlined already: then it fails). A loop's unit (on-stack replacement) inlines the closures its frame made before the loop, in the temps that hold them: guarded by class, startpc and outerContext (the frame's Context), else deoptimize. A loop's variant inlines too the closures other frames made (a block passed to `do:`, `inject:into:`) that the frame holds (its first 64 slots), or that such a closure's outer temps hold (the first 32 of each Context out from it): guarded by class, startpc and their outerContext's method (one guard, which leaves a loop as a class guard does, and with it the loads of the outerContext and its receiver: none of these ever changes); their outer temps and `self` through the closure. A loop that sends nothing loads an outer temp it does not store into once, where it is entered, and finds there where the others are: the slots of the frame their Context is married to, or the Context (what else may run, at an interrupt check, runs when the code has left the unit); one that a single store on every turn writes (no other store of a temp of that index, no read through another closure) is a value of the loop, a phi of what it held at the entry (guarded there a SmallInteger if the store writes one) and what the store wrote, and the store stays: `do:`'s `sum := sum + each`. So is a field of an object from before such a loop that one store on every turn writes (no other store into a field of that index, nor into an outer temp): `nextLine`'s `position := position + 1`. In the variant of an inherited method's loop the receiver is of the class the variant is for (guarded once at the entry), so sends to `self` find their methods (`SequenceableCollection>>do:` of a String reads its Characters inline); a frame slot the loop only reads is taken for the class of the object it holds when the unit is compiled, guarded there too (failing, the interpreter continues at the loop's head and the loop's units take no slot for anything again). Not those with `^`, `thisContext` or more than 200 bytecodes; anything else the compilation cannot do in one makes it start over calling that closure. `^` in an inlined block is a jump to the home activation's return; in a block's unit it deoptimizes, and the unit is not optimized again.

**Passes** (`OptPasses`): unreachable blocks, trivial phis, phis of SmallIntegers (a loop's counter, a running sum) typed as such, guards and casts of SmallIntegers dropped (arithmetic sees a constant operand behind them), arithmetic on two SmallIntegers left without its Float path (a phi's operand out of such a path does not count, so a counter beside Float arithmetic is a SmallInteger too), phis of SmallFloat64s typed as such and carried on doubles, their boxes left to the stores and returns after the loop (below), a method's or block's unit's guards of its receiver's class (no activation changes it) moved to its entry, after the entry's interrupt check, where they become one (unless they guard different classes, or one so hoisted failed there: `deoptHoisted`), global value numbering over the dominator tree (guards, arithmetic, comparisons, Float conversions and doubles, constants; a field load as one in a dominating block with nothing on any path between that may run Smalltalk or stores into a field (`memoryKeptFrom:to:mark:`; stores into indexed slots never write a named field), nor a store but into another field in the blocks themselves; a load after a store into the same field of the same object is the value stored, its SmallInteger guard gone), critical edges split, guards hoisted out of loops, unused pure nodes, reverse postorder. **Registers** (`OptRegalloc`): linear scan (Poletto and Sarkar) over one interval per value: x0–x13, x18 (Linux, UEFI), x26–x28, doubles d16–d31; a value without a register lives in its slot (the interval ending last is spilled), and a value live across a safepoint (in its live set after it, not merely inside its interval: an inner loop's values span the outer loop's code placed between its blocks) also has a home slot in the frame (an argument's is its own slot, a guard's result its input's; a double's is a raw slot); a guard's result takes its input's register, shared while the input lives on (neither is spilled for another value then), so a guard moves nothing, stored at its definition, or on the slow path of the interrupt checks if they are the only safepoints it crosses, and reloaded after the safepoint; constants are rematerialized.

**Unboxed Floats in loops.** A phi of SmallFloat64s is typed as one: every operand a box, a Float constant, a value of that class or such a phi; in a loop's unit also a frame slot that held one when the unit was compiled, guarded where the unit is entered (failing, the interpreter continues at the loop's head). It has a twin on doubles, a phi of the doubles of those boxes, of the constants and of those phis' twins (any other operand is decoded where it flows in, no check), and what unboxed the phi reads the twin: a running sum stays on doubles around its loop, across nested loops and where branches meet. A phi whose box nothing needs is gone. Frame states name its twin (deoptimization boxes it). A store into a field or an element, or a return (not a block's `^`), that runs no more often than the phi (after the loop, for a loop's own phi) boxes the twin itself, right before, with its own frame state: out of SmallFloat64's range it deoptimizes, the interpreter stores or returns, and that site reads a box from then on. A box in a loop that only such stores and returns after the loop read is made there instead, the same way. Anything else that reads the phi or the box needs it boxed (a send, a store in the loop, a guard, arithmetic with a SmallInteger path, an activation's receiver, a phi that is not of SmallFloat64s), as does every phi and box that flows into one that is: these are boxed beside the chain of doubles. **Escape analysis** (`OptPasses>>scalarReplace:`, flag `escape`). Right after the IR is built (before `typePhis`, so every later pass sees plain values), an object `basicNew` makes in eden (fixed fields only, at most 16; the `NF_ALLOC` send) whose every use is a load or a store of one of its fields (not a store of it anywhere), a class guard of its class, or a frame state after it, is not made: over the blocks it dominates, in reverse postorder, a load is the value its field holds there (nil before any store), a store goes, and where ways meet with different values, or a loop comes around, the field is a phi (`startOf:candidate:`; operands filled once every block is done; trivial ones go in `simplifyPhis`). So `p := i @ (i + 1). s := s + p x + p y` in a loop allocates nothing (32 bytes a turn before), and `p setX: p x + i setY: p y - i` on a Point from before a loop keeps its fields in the loop's phis. A send of it (inlined methods are no sends: `initX:y:` is two stores), a return, a phi, `==`, a store of it into anything, an indexed access, escapes it, and it is made as before. A frame state that names it names an `O_VOBJ` instead: a node in no block, its class `tcls`, the allocation `aux`, its fields' values at that point the operands `args`; the states that name it are copied where the fields differ (`virtualState:candidate:`, one copy per state while they stay the same; `roomFor:` checks the IR's arrays have room first). Such values are frame state values everywhere: `countUses` (`useValue:`), `resolveOperands` (the args of every node), `unboxStates` (a box only states and objects name: its double), `state:enteredFrom:of:` (a hoisted guard's state: the loop's phis among the fields too, `vobj:enteredFrom:of:`), the allocator's liveness, safepoint lists and intervals (`safeValue:in:`, `setStateValue:in:`, `extendStateValue:to:`): a field's value lives as long as a state that names the object. The record lists it with the closures never made: `-1`, its class's pool index, its field count, and after that list the fields' locations, objects in order (`recordState:kind:node:inSlots:`; one entry per allocation in a record, however many slots name it: `==` holds after deoptimization). `decode:` reads the fields first into deoptVals (the innermost activation's values stay last), and once the frames are written and the closures made, `makeObjects:` allocates each object (every value that was it becomes it) and fills its fields, for deoptimization and for `materialize:` (frames made Contexts: thisContext, the debugger, process switches). Nothing changes for become: (a send: the object escapes), identity hashes (a send) or the profiler (it reads no values). AWFY CD: 518 to 456 MB allocated in 10 laps (`Vector3D` temporaries of `findIntersection:`), 2.7 % faster; what is left is objects stored (`RedBlackTree` nodes), passed to calls that are not inlined (`recurse:...voxel:`'s `Vector2D`s go to `isInVoxel:motion:`, over 200 bytecodes) or merged by a phi (`InsertResult` from `treeAt:insert:`'s two returns). `SAMALTAK_OPT_TRACE` prints how many allocations a unit did not make.

**Code and frames** (`OptCodegen`). An optimized frame is a frame: x19–x22 as in the lower tier, the root activation's arguments in their slots, then home slots, then raw slots (the IEEE bits of doubles, from the header's `rawBase`, after the frame's temps: the collector, its verifier and a widowed Context skip them) and the outgoing receiver and arguments; its `pc` is the bytecode size plus a safepoint number (stored at its own safepoints, derived from the return map in calls). Method and block units start with the entry of calls as baseline code makes them, then the prologue for callers that pushed the frame; a method takes its receiver from x0, where calls bring it (the prologue loads it there). Blocks go in reverse postorder, but a loop's back edge right after the comparison that branches to it (a turn takes one branch). nil, true and false come from x23–x25. The generator knows which registers hold which slots, from what it emitted since the last label (a slot load or store makes its register hold the slot, other writes, calls and jumps undo that): such a slot is not loaded (moved if another register holds it) nor stored again; so with constants (a register that loaded one holds it) and with a value's class word (a type switch's cases load it once). Heap constants, the classes class checks compare with among them, are in the JitState's `oopTable` (2048 words, placed by identity hash as code is generated, GC roots, emptied when the code cache is flushed): one `ldr` from x22 where a pc-relative literal is two operations on the Cortex-X925 (x86: class checks compare with the word; other constants stay in the pool). A class check is `tst #7`, `csel` (x22 for an immediate), `ldr` of the class word, `ldr` of the class from the table, `cmp`, `b.ne`. The check after a call that the code is still valid is a pc-relative `ldr` of the header's flags word and a `tbnz`. Out-of-line paths after the code: guard failures, interrupt checks, brace Arrays the runtime makes, store barriers, deoptimization after a call, resumption after a call (the interpreter returned into the frame: the result from its slot), the stack check, the bottom frame's return (a unit of more than 32 KB reaches them from its `tbz`s through veneers: CD's and Havlak's biggest, some 60 KB). The header holds the safepoint table, the deoptimization records (kind, the send, per activation method, closure, receiver, pc and the location of every slot: register, slot, constant, sunk closure, a double's d register or raw slot), the dependencies, the inline caches and the return map; an oop pool after the code (pc-relative loads, GC roots), then the inline caches' literals. The listing (`machineCodeFor: #opt`) shows the root method's bytecodes and the inlined activations' pcs.

**Deoptimization** (`OptRuntime`). A failed guard jumps to a stub that saves the registers; the record rebuilds the activations as frames (a double that is a SmallFloat64 becomes one, others one BoxedFloat64 per location once the frames are written, and the closures and objects never made are made), the interpreter continues the innermost one, and the site's feedback learns what failed. A failure the feedback had not reported, or one in code compiled before the site's feedback last changed, invalidates the code at once (it compiles differently next time), so does the ninth deoptimization; a site that fails again in code compiled with what it reports now is marked: no speculation there next time; a unit is compiled at most 32 times. `materializeAll` (process switches, Smalltalk looking into an optimized frame) turns an optimized frame into a Context per activation; the interpreter returning into an optimized frame resumes it at its safepoint. Invalidation (lazy): a method added or removed for a selector the code inlined or speculated on (`flushCacheForSelector:`), become of a method, an object given another class in place (`changeClassTo:`: code may know the class of what it made or guarded; all of it goes): the code is marked dead, frames running it deoptimize when control comes back to them (a check after every call), calls into it go to the lower tier. Switching the mode away from `opt` makes every optimized frame Contexts first.

**Contexts.** Methods with a marker primitive (`on:do:`, `ensure:`, `ifCurtailed:`) are not optimized, so the frames the exception code reads and writes through their Contexts are plain; methods with `thisContext` or Context's mediated forms (0x81 of fields 0–2, 0x88) neither, and none of these is inlined. An optimized frame is married only when it is entered married (a loop's unit; its return widows it). Smalltalk does not look into one: marrying it (the sender of a married Context) or reading a married one's pc, stackp or slots flushes the frames instead. A suspended frame cannot be deoptimized in place without moving every frame above it. Sends to Contexts link and call like any other.

**Stress.** `--jit-flags eager` optimizes at the first count; `deopt` makes optimized code take every 37th slow path it passes (guards, interrupt checks, returns from calls) and deoptimize there, without feedback. `make test-jit` runs the image's tests under `--jit opt` with eager and with eager,deopt; `vm/tests/run.sh` the mini kernel's under both (with the GC stress) and the default thresholds; `JitOptRuntimeTest` covers deoptimization of a failed speculation (and none where nothing was speculated: `perform:`, `doesNotUnderstand:`, SmallIntegers beside Floats, BoxedFloat64s, SmallInteger arithmetic that baseline code sent, SmallIntegers where LargeIntegers were), invalidation of inlined code while it runs, a send that never ran (a deoptimization point: the closure it takes is not made, the loop is optimized; taken, a send from then on), closures that store temps across loops, closures a loop's unit inlines from its frame, calls into machine code (no sends through the runtime: `optRuntimeSends`), process primitives that switch no process, `perform:` of a constant (inlined), `at:` of a String argument (inline after one deoptimization), a count shared with a method that failed to compile, brace Arrays (inlined, across interrupt checks where the collector runs, more than 64 elements), a loop's values across interrupt checks where Processes switch and the collector runs, a loop's counter beside Float arithmetic (a SmallInteger: no Float path, converted without a test; a sum that overflows), a loop's unit that took the frame's SmallIntegers entered with them again and with a Float, Float loops on doubles (across those interrupt checks; a loop's unit entered with a SmallInteger, a Fraction or nil, and one compiled for a SmallFloat64 entered with one, a SmallInteger or a BoxedFloat64; a loop that sends; more running Floats than d registers; running Floats without boxes in their loops: boxed where they are returned or stored after it, by the interpreter out of SmallFloat64's range; across nested loops, a conditional's phi and a swap; where a guard fails in the loop; one the loop sends, boxed there), deoptimization with dead temps (straight code, branches, loops, nested Float loops, blocks, a loop's unit) and a frame made a Context with nil in its dead temps, the stress, the listing.

**Flags** (`--jit-flags`, all on by default): `inline` (methods), `blocks` (closures), `prims`, `unbox` (Floats on doubles), `calls` (direct and block calls), `ffi-site` ([bound FFI sites](#bound-ffi-sites)), `alloc`, `gvn`, `hoist`, `live` (frame states name only the temps still read; off: every temp), `bg` (background compilation), `cold` (sends that never ran deoptimize; off: inline caches), `escape` (objects that do not escape are not made); `eager` and `deopt` are off.

Not done: loop-invariant code motion other than guards', Float decodings' and SmallInteger sums' and differences', ranges of phis of loops counting down or with more than one way around, and bounds checks of indices other than affine ones in a counted loop's counter and induction variables or what ranges bound (a `whileTrue:` loop's derived index keeps its check), escape analysis of objects merged by phis, passed to calls or escaping on one path only (partial escape analysis: made where they escape), of indexed objects, unboxed Floats across calls, in fields and in elements (a store boxes, a load unboxes under a check: NBody's `advance`), in a loop's variable that starts as a SmallInteger (`sum := 0`: in the method's unit not a phi of SmallFloat64s, boxed every time around) or that arithmetic with a SmallInteger path reads (SpectralNorm's `vBv / vv`: its boxes stay in the loop), SmallIntegers known for a method's arguments or what it loads (a counter compared with such a limit beside Float arithmetic keeps both paths there), inlining of closures made elsewhere other than in a loop's variant (a method's unit calls a block passed in through the block stub).

### Bound FFI sites

The optimizing tier can specialize an ordinary positional FFI send with a
known receiver class or monomorphic feedback. It checks the resolved
method's primitive (`ffiBoundInvoke`) and arity, not the selector's spelling.
A selector dependency invalidates the code on method installation or removal.
Array invocation, `super` sends, and reflective dispatch do not use this path.

The compiler can seed a site with a known, already prepared binding.
Otherwise an empty or revoked site can learn one at run time. The cold
helper checks lookup and arity again, neither prepares nor invokes the
binding, and leaves the original send to run. Preparation and snapshot
rebinding remain on the normal invoke path.

The guard checks that the code is live and that the receiver matches the
binding's weak owner slot, publication serial and session-tagged token.
The collector updates or clears the weak slot; the serial prevents slot
reuse from validating an old site. A different live binding takes the
original send without replacing the cached binding. Site storage is
bounded; if unavailable the compiler emits the ordinary send. Sites are
discarded with the JIT cache and are not saved in snapshots.

A hit calls the cached wrapper entry with the outgoing positional arguments
in the caller's slots, without pushing a Smalltalk callee frame: its one C
argument is the address of the first of them, for any arity up to sixteen.
The wrapper converts each into its native register or, past the argument
registers, its outgoing stack slot (docs/ffi.md, Generated call wrappers), so
a call with stack arguments needs nothing else at the site and takes the same
bound path; there is no separate fallback for them. The wrapper
still validates its arguments. Its rejection sentinel becomes `false`;
native zero and `void` already have Smalltalk results. For `i32`, `u32`
and `void`, conversion cannot collect. For `i64`, `u64`, `f64` and `f32` (and
the wide results the site treats as `f64`), the caller marks its safepoint and spills live values; the boxing helper makes
the frame visible to the collector before it can allocate. After the wrapper returns, the continuation
reloads live values and handles interrupts or deoptimization **after** the
send, never by replaying native work. Native targets must not reenter the VM.

## x86-64

The code generators are the same on both CPUs: they emit arm64's instructions with arm64's registers, and on x86-64 `Amd64Assembler` emits each as the x86-64 instructions that do what it does (an `add` with three registers a `lea`, a `tbz` a `test` or `bt` and a `jcc`, `ldp` two `mov`s, `csel` a `cmov`, ...). Where x86 has a better sequence or no counterpart, the generator branches on `asm isX64` (optimized code's indexed loads and stores address their element as one operand, `[object + index·size + header and fixed fields]`, the index 1-based where the loop checked its bounds before it), which the translator folds per CPU (docs/lowtalk.md, CPUs), so the arm64 build compiles the same C as before the port. `tools/lowering-check.sh` runs random programs of these instructions as x86-64 and, under `qemu-aarch64`, as arm64 (on an arm64 host the x86-64 ones under `qemu-x86_64`): they must leave the same registers and memory. On an arm64 Linux host without an x86-64 cross compiler, `tools/x86-toolchain.sh` downloads one without root (Ubuntu's cross gcc, glibc and `qemu-user-static`, unpacked into `~/.cache/samaltak/x86-toolchain`), which `lowering-check.sh` then uses by itself; longer programs find more (`tools/lowering-check.sh build/samaltak.image SEED 3000 40`).

**Registers.** x0–x5 are rdi rsi rdx rcx r8 r9 (C's argument registers: the runtime's arguments are where SysV wants them), x9 rax, x10 r14, x11 r15, x16 r10, x17 r12, x19 rbp, x20 rbx, x21 r13, d0–d15 xmm0–xmm15; r11 is the assembler's scratch, rsp is sp. x22 has no register: the JitState is a global, so its words are `[rip + disp32]` (the code cache is in the VM's BSS, within 2 GB); x23–x25 (nil, true, false) are its words, read where they are used, and their reloads after calls are nothing. Every other arm64 register (x6–x8, x12–x15, x18, x26–x28) is a word of `asmRegs`, a register file in memory: correct, slower; the code generators keep out of them where it matters. So baseline code's operand-stack registers are x0–x5, it has no loop temps in registers, and optimized code allocates x0–x5, x9 and x21 (r13: optimized code does not keep the receiver there) and d2–d15; its scratch registers are x10, x11, x16, x17.

**Flags.** Most x86 instructions write the flags, arm64's only those that say so. The assembler tracks the kind of the last instruction that set them (subtract: the carry is inverted; add; logical; floating point compare: an unordered result sets the parity flag, so EQ, NE, MI, LS and their opposites take two tests; multiply: overflow; `bt`, which tests one bit beyond a 32-bit immediate's reach: the bit in the carry, for EQ and NE), across labels too (each branch brings its kind, a label merges them), and fails to compile (`ASM_ERR_FLAGS`) code that reads flags its own x86 code destroyed, rather than run it wrong. `muls:with:with:` multiplies with the overflow in the flags (`imul`, `jo`) where arm64 compares `smulh`. `ccmp`/`ccmn` are a short jump on the condition over the compare and a jump over flags made by a compare (an add for `ccmn` of registers) of constants in r11 that read as the nzcv: only flags a subtraction can give (0, 2, 3, 6, 8, 9, 10; and 4 after an addition), others fail (`ASM_ERR_OPERAND`).

**Frames and calls.** `call` pushes the return address: that word is an activation's native record (8 bytes, where arm64's x29/x30 pair is 16; `canonicalizeBelow:` reads it at `baseRecord − 8·(f − baseFrame)`), and `stp`/`ldp`/`str`/`ldr` of x29 or x30 with sp are nothing. The prologue is 12 bytes (`JIT_PROLOGUE_BYTES_X64`). A stub that calls C aligns the native stack to 16 (machine code keeps it 8-aligned), keeps xmm8–xmm15 (baseline code's unboxed Floats; SysV saves no xmm register) and moves the result from rax to x0 (`callC:`); the primitive and copy stubs, entered only by sends and calls (baseline code boxes its Floats before one, optimized code loads its doubles from their raw slots again after one), do not keep them (`callCFromSend:`); `jit_enter` saves SysV's callee-saved registers and asmRegs' x26–x28. Call sites are `call rel32`, their displacement the site (`siteBl`); a polymorphic inline cache's cases are 14 bytes each (`cmp r10, [rip + class]`, `jne`, `jmp`), a redirected unchecked entry starts with a 5-byte `jmp` over its stack check (`cmp rbx, [rip + limit]`, its first byte 16r48 and the 4 bytes after it kept in `entryWord`). The stack, interrupt and tier-up checks compare or decrement the JitState's words in memory.

**What registers hold.** `OptCodegen>>catchUp` decodes the x86 code it emitted as it does arm64's: `Amd64Assembler>>effectAt:` tells what an instruction does (a 64-bit load or store of an `rbx` slot, a move, a write; calls, jumps, pushes and other stores into the frame forget all; a short jump forward over the assembler's own code counts as what that code does), in arm64's registers; an instruction it does not know ends what is known.

Not done on x86: loop temps in registers (no registers to spare), BMI2's flag-free shifts. Speed: docs/benchmarks.md (Are We Fast Yet, x86-64).

Where to gain, by the evidence:

1. **Class checks**: the commonest instruction kind in machine code of List (51 %), DeltaBlue (31 %), Richards (30 %), Queens (27 %), Towers (25 %) and Havlak (21 %): six instructions with a load of the expected class from the literal pool, again for a receiver checked before a call (its value reloaded from the frame loses what was known about it) and for each field send to the same object. Keeping the known class of values across calls and reloads, checking an object once, and cheaper checks would remove most of them. (Where an object is first touched, as in List's walks, the check also takes the blame for the load's latency.) Done since: no move after a guard, a type switch's class word loaded once, the class from the JitState (one operation where the literal was two), field loads (and their checks) numbered across blocks, the receiver checked once at a unit's entry: class checks 42.7 % of List's operations, 22.3 % of DeltaBlue's, 20.0 % of Richards'; List 17 %, Towers 18 %, Queens 8 %, Richards 6 %, Havlak 6 % faster. What is left of them checks values loaded from fields (the class of what a field holds is not known; List's walks, DeltaBlue's constraints' variables).
2. **Frame traffic**: every value is stored into its frame slot as it is computed, all of them reloaded after each call, and every temp set to nil at entry: 17 % of Permute's and 19 % of Mandelbrot's instructions (the inner loop stores its three Floats and three integers into the frame every iteration), 10–12 % in Towers, Havlak, DeltaBlue, Json, Storage. Only the values live at a safepoint need slots, and only when it is reached (deoptimization metadata saying which register holds which slot instead).
3. **Float decoding**: NBody's 52 % arithmetic is mostly turning immediate Floats read from instance variables into doubles: per field read a SmallInteger test, the tag test, then `lsr`, a 64-bit constant, `add`, `cmp`, `csel`, `ror`, `fmov`, about 12 instructions (and encoding them back on stores). Keeping the bodies' coordinates unboxed across the loop, a constant hoisted into a register, and decoding only the Float case when the feedback saw only Floats would cut most of it.
4. **Loop overhead**: Sieve's inner loop spends 12 % of its instructions polling for interrupts (`ldr` of the flag, `cbnz` every iteration), 11 % on overflow checks of its index and 9 % on register moves (a constant materialized again each iteration, the result computed into x16 and then moved to its register); Mandelbrot 6 % polls and 20 % moves (`fmov` of its loop-carried doubles at the back edge). Range analysis for induction variables (no overflow check, no bounds check), polling once per many iterations of a counted loop, and coalescing the moves of loop-carried values.
5. **Code that is not optimized**: Richards spends 13.5 % of its cycles in the `baseline block value` stub (blocks the optimizer did not inline, called through the runtime's stub); Json 11 % in `baseline` code (`String>>compareWith:` 8.4 %), Havlak 9.7 % (`Behavior>>basicNew` 4.3 %); Sieve 6.8 % in the VM's `alloc_obj` (its `Array new: n` allocated in C); DeltaBlue 12 % in the VM, part of it still compiling after 100 iterations (the register allocator 1.8 %).
